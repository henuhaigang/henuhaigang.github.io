# Tomcat 架构原理与性能调优深度解析

> **一句话概括**：Tomcat 不是简单的 Servlet 容器，而是 **Coyote（连接器）+ Catalina（容器）+ Jasper（JSP引擎）** 三位一体的精密协作体；Coyote 负责网络 I/O 与协议解析，Catalina 负责容器生命周期与请求分发，Jasper 负责动态编译；吃透 **Server → Service → Engine → Host → Context → Wrapper** 六层容器与 **Acceptor → Poller → Worker** 三级线程模型，才能在万级并发下做到零宕机。

**三大核心组件**：

| 组件 | 模块 | 职责 | 对应源码 |
|------|------|------|----------|
| **Coyote** | Connector、ProtocolHandler、Endpoint | 网络通信、协议解析、Socket 管理 | `org.apache.coyote`、`org.apache.tomcat.util.net` |
| **Catalina** | Server、Service、Engine、Host、Context、Wrapper | 容器管理、生命周期、请求分发 | `org.apache.catalina` |

> **12年经验一句话**：面试官问“Tomcat 是什么”，不要只答“Servlet 容器”，要答“**基于 Coyote 的高性能 I/O 层 + 基于 Catalina 的分层容器 + 基于 Jasper 的动态编译**”的三层架构。

## 二、容器层级：Server → Service → Engine → Host → Context → Wrapper

### 2.1 容器层级与 server.xml 映射

```xml
<!-- conf/server.xml 完整映射 -->
<Server port="8005" shutdown="SHUTDOWN">
  <!-- Server：最顶层，代表整个 Tomcat 实例 -->
  <Service name="Catalina">
    <!-- Service：服务抽象，关联 Connector 与 Engine -->
    
    <!-- Connector：连接器，监听端口，对接外部请求 -->
    <Connector port="8080" protocol="HTTP/1.1"
               connectionTimeout="20000"
               maxThreads="200"
               minSpareThreads="10"
               acceptCount="100" />
    <Connector port="8009" protocol="AJP/1.3" redirectPort="8443" />

    <!-- Engine：引擎，处理 Service 内所有请求，Host 容器 -->
    <Engine name="Catalina" defaultHost="localhost">
      
      <!-- Host：虚拟主机，域名隔离 -->
      <Host name="localhost" appBase="webapps"
            unpackWARs="true" autoDeploy="true">
        
        <!-- Context：Web 应用，对应一个 WAR/目录 -->
        <Context path="/myapp" docBase="myapp" reloadable="false">
          <!-- Wrapper：Servlet 包装器，对应一个 Servlet -->
          <!-- 由 web.xml / 注解动态生成，无需在 server.xml 显式配置 -->
        </Context>
        
      </Host>
    </Engine>
  </Service>
</Server>
```

**层级关系与职责**：

```
Server (1) ──包含──► Service (1..N) ──包含──► Connector (1..N)
   │                      │
   │                      └──包含──► Engine (1)
   │                                     │
   │                                     └──包含──► Host (1..N)
   │                                                      │
   │                                                      └──包含──► Context (1..N)
   │                                                                        │
   │                                                                        └──包含──► Wrapper (1..N)
```

| 容器 | Cardinality | 职责 | 实现类 |
|------|-------------|------|--------|
| **Server** | 1 | 代表 Tomcat 实例，监听 shutdown 端口，管理 Service 生命周期 | `StandardServer` |
| **Service** | 1..N | 关联多个 Connector 和一个 Engine，承上启下 | `StandardService` |
| **Engine** | 1 | 为 Service 处理所有请求，管理多个 Host | `StandardEngine` |
| **Host** | 1..N | 虚拟主机，域名维度隔离，管理多个 Context | `StandardHost` |
| **Context** | 1..N | 一个 Web 应用，隔离类加载器、Session、Servlet | `StandardContext` |
| **Wrapper** | 1..N | 一个 Servlet 的包装器，管理 Servlet 生命周期 | `StandardWrapper` |

### 2.2 容器共同基类：ContainerBase 与生命周期

```java
// 所有容器的抽象基类
public abstract class ContainerBase implements Container, Lifecycle {
    // 子容器
    protected final HashMap<String, Container> children = new HashMap<>();
    // Pipeline 责任链
    protected final Pipeline pipeline = new StandardPipeline(this);
    // 后台线程，定期检查 reload、过期 Session
    protected Thread backgroundProcessor;
    
    @Override
    public void addChild(Container child) {
        children.put(child.getName(), child);
        child.setParent(this);
    }
    
    @Override
    public void invoke(Request request, Response response) {
        pipeline.getFirst().invoke(request, response);
    }
}
```

## 三、Lifecycle 统一生命周期机制

### 3.1 为什么需要统一生命周期？

Tomcat 有 6 层容器 + Connector + Executor + Realm 等几十个组件，启动/停止顺序必须严格有序。Lifecycle 就是解决**组件级联启停**的模板方法模式。

```java
// org.apache.catalina.Lifecycle
public interface Lifecycle {
    public enum State {
        NEW, INITIALIZING, INITIALIZED,
        STARTING_PREP, STARTING, STARTED,
        STOPPING_PREP, STOPPING, STOPPED,
        DESTROYED, FAILED
    }
    void init() throws LifecycleException;
    void start() throws LifecycleException;
    void stop() throws LifecycleException;
    void destroy() throws LifecycleException;
    void addLifecycleListener(LifecycleListener listener);
}

// 抽象实现：LifecycleBase
public abstract class LifecycleBase implements Lifecycle {
    private volatile State state = State.NEW;
    
    @Override
    public final synchronized void init() throws LifecycleException {
        setStateInternal(State.INITIALIZING, null, false);
        initInternal();  // 模板方法，子类实现
        setStateInternal(State.INITIALIZED, null, false);
    }
    
    @Override
    public final synchronized void start() throws LifecycleException {
        if (state == State.NEW) init();
        setStateInternal(State.STARTING_PREP, null, false);
        startInternal(); // 模板方法
        setStateInternal(State.STARTED, null, false);
    }
    
    // stop/destroy 同理
    protected abstract void initInternal() throws LifecycleException;
    protected abstract void startInternal() throws LifecycleException;
    protected abstract void stopInternal() throws LifecycleException;
    protected abstract void destroyInternal() throws LifecycleException;
}
```

### 3.2 级联启动流程

```java
// StandardServer.startInternal()
protected synchronized void startInternal() throws LifecycleException {
    // 1. 触发监听器
    fireLifecycleEvent(CONFIGURE_START_EVENT, null);
    setState(State.STARTING);
    
    // 2. 启动所有 Service
    for (Service service : services) {
        service.start(); // 递归级联
    }
}

// StandardService.startInternal()
protected void startInternal() throws LifecycleException {
    // 1. 启动 Engine（容器链）
    engine.start();
    // 2. 启动所有 Executor 线程池
    for (Executor executor : executors) {
        executor.start();
    }
    // 3. 启动所有 Connector（网络监听）
    for (Connector connector : connectors) {
        connector.start(); // 启动 Endpoint，开始 accept
    }
}
```

**启动顺序图**：

```
Bootstrap.main()
  ↓
Catalina.load() → 解析 server.xml → 创建层级对象
  ↓
Catalina.start()
  ↓
StandardServer.start()
  ├─ StandardService.start()
  │    ├─ StandardEngine.start()
  │    │    └─ StandardHost.start()
  │    │         └─ StandardContext.start()  // 部署 WAR，启动 Wrapper
  │    │              └─ StandardWrapper.load() // 加载 Servlet
  │    ├─ Executor.start()
  │    └─ Connector.start()
  │         └─ ProtocolHandler.start()
  │              └─ Endpoint.start() → Acceptor/Poller 线程启动
  ↓
监听端口，等待请求
```

> **12年踩坑**：`Context reloadable="true"` 会监听 `WEB-INF/classes` 变化自动 reload，原理就是 `ContainerBackgroundProcessor` 线程定时检查。生产环境必须设为 `false`，否则频繁 GC + 类加载器泄漏。

## 四、Pipeline-Valve 责任链模式

### 4.1 设计思想

每个容器都有一个 Pipeline，Pipeline 中串联多个 Valve（阀门），最后一个是 BasicValve。请求在容器间传递，本质是在 Valve 链中传递。

```java
// org.apache.catalina.Pipeline
public interface Pipeline {
    Valve getFirst();
    Valve getBasic();
    void addValve(Valve valve);
}

// org.apache.catalina.Valve
public interface Valve {
    Valve getNext();
    void setNext(Valve valve);
    void invoke(Request request, Response response) throws IOException, ServletException;
}

// 标准实现
public class StandardPipeline implements Pipeline {
    protected Valve basic;  // 兜底 Valve
    protected Valve first;  // 链头
    
    @Override
    public void invoke(Request request, Response response) {
        first.invoke(request, response);
    }
}
```

### 4.2 各层容器的默认 Valve 链

```
请求进入：Connector → Engine → Host → Context → Wrapper

Engine Pipeline:
  AccessLogValve → ... → StandardEngineValve (basic)
                            ↓ 选择 Host

Host Pipeline:
  AccessLogValve → ErrorReportValve → StandardHostValve (basic)
                                        ↓ 选择 Context

Context Pipeline:
  ... → StandardContextValve (basic)
            ↓ 选择 Wrapper

Wrapper Pipeline:
  ... → StandardWrapperValve (basic)
            ↓ 调用 Servlet.service() → FilterChain → Servlet
```

```java
// StandardEngineValve 核心逻辑：选择 Host
public final class StandardEngineValve extends ValveBase {
    @Override
    public void invoke(Request request, Response response) {
        Host host = (Host) request.getHost();
        if (host == null) {
            response.sendError(400);
            return;
        }
        host.getPipeline().getFirst().invoke(request, response);
    }
}

// StandardHostValve：选择 Context
public final class StandardHostValve extends ValveBase {
    @Override
    public void invoke(Request request, Response response) {
        Context context = (Context) request.getContext();
        if (context == null) {
            response.sendError(404);
            return;
        }
        context.getPipeline().getFirst().invoke(request, response);
    }
}

// StandardWrapperValve：调用 Servlet
public final class StandardWrapperValve extends ValveBase {
    @Override
    public void invoke(Request request, Response response) {
        Wrapper wrapper = (Wrapper) getContainer();
        Servlet servlet = wrapper.allocate(); // 从池/单例获取
        // 创建 FilterChain，执行 filter → servlet
        ApplicationFilterChain filterChain = ApplicationFilterFactory.createFilterChain(request, wrapper, servlet);
        filterChain.doFilter(request.getRequest(), response.getResponse());
    }
}
```

> **扩展点**：自定义 Valve 可插入任意容器层级，常用于鉴权、限流、灰度、审计。例如在 Engine 层插入全站限流 Valve，在 Context 层插入业务鉴权 Valve。

### 5.2 Endpoint 三大线程模型

Endpoint 是 Coyote 的 I/O 核心，负责 TCP 连接管理。

```
                ┌─────────────┐
   Client ─TCP─►│  Acceptor   │  (1个或多个，阻塞 accept)
                └──────┬──────┘
                       │ SocketChannel
                       ▼
                ┌─────────────┐
                │   Poller    │  (1-2个，Selector 轮询)
                └──────┬──────┘
                       │ 读就绪事件
                       ▼
           ┌─────────────────────┐
           │   Worker 线程池      │  (maxThreads 个，如 200)
           │  Executor           │
           │  处理 HTTP 解析+业务 │
           └─────────────────────┘
```

**源码映射** (`org.apache.tomcat.util.net.NioEndpoint`)：

```java
public class NioEndpoint extends AbstractEndpoint<NioChannel, NioSocketWrapper> {
    // Acceptor 线程：阻塞 accept
    protected class Acceptor implements Runnable {
        @Override
        public void run() {
            while (running) {
                // 1. 阻塞等待新连接
                SocketChannel socket = serverSock.accept();
                // 2. 封装并注册到 Poller
                NioChannel channel = new NioChannel(socket);
                Poller poller = getPoller0(); // 轮询选择 Poller
                poller.register(channel); // 注册 OP_READ
            }
        }
    }
    
    // Poller 线程：Selector 轮询
    public class Poller implements Runnable {
        private Selector selector;
        private SynchronizedQueue<PollerEvent> events;
        
        @Override
        public void run() {
            while (true) {
                // 1. 处理注册事件
                events();
                // 2. select 阻塞等待 I/O 就绪
                int keyCount = selector.select(1000);
                // 3. 遍历就绪 key，分发给 Worker
                Iterator<SelectionKey> it = selector.selectedKeys().iterator();
                while (it.hasNext()) {
                    SelectionKey key = it.next();
                    NioSocketWrapper wrapper = (NioSocketWrapper) key.attachment();
                    if (key.isReadable() || key.isWritable()) {
                        // 交给线程池处理
                        executor.execute(new SocketProcessor(wrapper, SocketEvent.OPEN_READ));
                    }
                }
            }
        }
    }
    
    // Worker：处理 HTTP 协议
    protected class SocketProcessor implements Runnable {
        @Override
        public void run() {
            // 1. 解析 HTTP 请求行、头、体
            Http11Processor processor = new Http11Processor();
            processor.process(wrapper);
            // 2. 通过 Adapter 分发到 Engine
            adapter.service(request, response);
        }
    }
}
```

### 5.3 BIO vs NIO vs NIO2 vs APR

| 模式 | 协议配置 | I/O 模型 | 线程模型 | 适用场景 | Tomcat 10 默认 |
|------|----------|----------|----------|----------|----------------|
| **BIO** | `Http11Protocol` | 阻塞 I/O | 每连接每线程 | 已废弃，Tomcat 8.5 移除 | - |
| **NIO** | `Http11NioProtocol` | 非阻塞 Selector | Acceptor + Poller + Worker | **通用推荐，99% 场景** | **是** |
| **NIO2** | `Http11Nio2Protocol` | 异步 AIO | 异步回调 | 长连接、推送，性能略优但生态一般 | 否 |
| **APR** | `Http11AprProtocol` | Native (OpenSSL) | Native 线程 | 极致性能、HTTPS 卸载，需安装 `tomcat-native` | 否 |

```xml
<!-- 切换协议，只需改 protocol -->
<!-- NIO (默认) -->
<Connector port="8080" protocol="org.apache.coyote.http11.Http11NioProtocol" />
<!-- NIO2 -->
<Connector port="8080" protocol="org.apache.coyote.http11.Http11Nio2Protocol" />
<!-- APR -->
<Connector port="8080" protocol="org.apache.coyote.http11.Http11AprProtocol" />
```

**12年选型建议**：

```
需要 HTTPS 高性能？
  → 是：NIO + APR/OpenSSL（或直接前置 Nginx 卸载）
  → 否：直接 NIO

长连接/Server-Sent Events/WebSocket 多？
  → NIO2 或 NIO 均可，NIO 更成熟

追求极简运维？
  → NIO，无需 native 依赖
```

### 5.4 关键参数深度解析

```xml
<Connector port="8080" 
           protocol="HTTP/1.1"
           maxThreads="400"          <!-- Worker 线程池最大线程，默认200 -->
           minSpareThreads="50"      <!-- 最小空闲线程，默认10 -->
           acceptCount="500"         <!-- 等待队列长度，默认100 -->
           maxConnections="10000"    <!-- 最大连接数，NIO 默认10000 -->
           connectionTimeout="20000" <!-- 连接超时 20s -->
           keepAliveTimeout="60000"  <!-- keep-alive 超时 60s -->
           maxKeepAliveRequests="100"<!-- keep-alive 最大请求数 -->
           acceptorThreadCount="2"   <!-- Acceptor 线程数，默认1 -->
           pollerThreadCount="2"     <!-- Poller 线程数，默认1-2 -->
           compression="on"          <!-- GZIP 压缩 -->
           compressionMinSize="2048"
           compressableMimeType="text/html,text/xml,text/plain,application/json"
           />
```

**线程池与队列关系**（`AbstractEndpoint`）：

```
新连接 → Acceptor → Poller → Worker 线程池
                              │
                    ┌─────────┼─────────┐
                    │         │         │
                 队列未满   队列已满   线程已达 maxThreads
                    │         │         │
                    ▼         ▼         ▼
                 立即执行   排队等待   拒绝（触发 acceptCount 限制后的拒绝）
```

> **核心公式**：`maxThreads` 不是越大越好。线程过多会导致上下文切换、内存占用剧增。经验值：**`maxThreads = CPU核数 * (1 +  IO耗时/CPU耗时)`**。纯 API 服务 200-400，涉及大量 IO 的可到 800。

## 六、类加载器：打破双亲委派的经典案例

### 6.1 为什么要打破双亲委派？

- **隔离性**：不同 WebApp 的 `WEB-INF/lib` 可能有相同类库的不同版本（如 Spring 5 vs Spring 6），必须隔离。
- **灵活性**：WebApp 需要优先加载自己的类，而不是 JDK/容器提供的。
- **热部署**：Context reload 时，需丢弃旧 ClassLoader，创建新 ClassLoader 加载新类。

### 6.2 Tomcat 类加载器层级

```
                    Bootstrap (JVM, rt.jar)
                         ↑
                    Platform (JDK 9+, JDK 扩展)
                         ↑
                    System (classpath)
                         ↑
                    Common (Tomcat/lib, 容器与 App 共享)
                         ↑
              ┌──────────┴──────────┐
              │                     │
         Catalina                Shared
      (Tomcat 内部)           (所有 WebApp 共享，可选)
              │                     │
              └──────────┬──────────┘
                         ↑
              WebappClassLoader (每个 Context 一个)
              /WEB-INF/classes
              /WEB-INF/lib/*.jar
```

```java
// org.apache.catalina.loader.WebappClassLoaderBase
public class WebappClassLoaderBase extends URLClassLoader {
    @Override
    public Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        synchronized (getClassLoadingLock(name)) {
            // 1. 先在本地缓存找
            Class<?> clazz = findLoadedClass(name);
            if (clazz != null) return clazz;
            
            // 2. 关键：打破双亲委派，先尝试自己加载
            // 对于 WEB-INF/classes 和 WEB-INF/lib 的类，优先自己加载
            if (!name.startsWith("org.apache.")) { // 容器内部类除外
                try {
                    clazz = findClass(name); // 自己先找
                    if (clazz != null) return clazz;
                } catch (ClassNotFoundException e) {
                    // 找不到再委托父加载器
                }
            }
            
            // 3. 委托父加载器
            return super.loadClass(name, resolve);
        }
    }
}
```

**`delegate` 参数**（`Context` 配置）：

```xml
<!-- delegate="true" 表示严格双亲委派（父优先），false 表示子优先（默认） -->
<Context delegate="false" />
```

| `delegate` | 加载顺序 | 场景 |
|------------|----------|------|
| `false` (默认) | WebApp 优先 → 父加载器 | 应用隔离，推荐 |
| `true` | 父优先 → WebApp | 强制使用容器提供的库（如容器统一管理 JDBC 驱动） |

### 6.3 内存泄漏重灾区

**12年血泪教训**：Tomcat 热部署内存泄漏 90% 源于类加载器未释放。

```java
// 典型泄漏 1：ThreadLocal 未清理
public class MyServlet extends HttpServlet {
    private static ThreadLocal<Connection> holder = new ThreadLocal<>();
    // WebApp 卸载时，Tomcat Worker 线程仍持有 ThreadLocal → 持有 WebappClassLoader → 无法 GC
}

// 典型泄漏 2：JDBC 驱动未注销
// mysql-connector 静态注册到 DriverManager（由 System ClassLoader 加载）
// 持有 WebApp ClassLoader 引用
// 解决：ContextListener 中显式注销
@WebListener
public class CleanupListener implements ServletContextListener {
    @Override
    public void contextDestroyed(ServletContextEvent sce) {
        // 1. 注销驱动
        Enumeration<Driver> drivers = DriverManager.getDrivers();
        while (drivers.hasMoreElements()) {
            Driver driver = drivers.nextElement();
            if (driver.getClass().getClassLoader() == getClass().getClassLoader()) {
                DriverManager.deregisterDriver(driver);
            }
        }
        // 2. 清理 ThreadLocal
        // 3. 关闭线程池
        // 4. 停止 Timer
    }
}

// 典型泄漏 3：非守护线程未停止
// WebApp 启动的线程，ClassLoader 为 WebappClassLoader，线程存活则 ClassLoader 无法回收
```

public class SocketProcessor implements Runnable {
    public void run() {
        Http11Processor processor = new Http11Processor(endpoint);
        processor.process(socketWrapper); // 解析请求行、头、体
    }
}

// 3. Http11Processor 解析完成后，调用 Adapter
public SocketState process(SocketWrapperBase<?> wrapper) {
    Request coyoteRequest = wrapper.getRequest();
    Response coyoteResponse = wrapper.getResponse();
    // 解析 HTTP
    inputBuffer.parseRequestLine();
    inputBuffer.parseHeaders();
    // 适配到 Catalina
    adapter.service(coyoteRequest, coyoteResponse);
    return SocketState.CLOSED;

// 4. CoyoteAdapter：Coyote → Catalina 桥接
public class CoyoteAdapter implements Adapter {
    @Override
    public void service(Request req, Response res) {
        // 转换
        org.apache.catalina.connector.Request request = (Request) req.getNote(ADAPTER_NOTES);
        org.apache.catalina.connector.Response response = (Response) res.getNote(ADAPTER_NOTES);
        
        // 解析域名、URI，定位 Host/Context/Wrapper
        connector.getService().getContainer().getPipeline().getFirst().invoke(request, response);
        // 即 Engine.invoke()
    }
}

// 5. 最终到 StandardWrapperValve
public void invoke(Request request, Response response) {
    Servlet servlet = wrapper.allocate();
    ApplicationFilterChain chain = ApplicationFilterFactory.createFilterChain(request, wrapper, servlet);
    chain.doFilter(request, response); // 执行 Filter → Servlet
}

```java
// 源码：AbstractEndpoint 创建线程池
public void createExecutor() {
    if (executor == null) {
        // 默认：TaskQueue + ThreadPoolExecutor
        // TaskQueue 是 LinkedBlockingQueue 的子类，关键改写了 offer 逻辑
        TaskQueue taskqueue = new TaskQueue(maxQueueSize);
        TaskThreadFactory tf = new TaskThreadFactory(namePrefix, daemon, getThreadPriority());
        executor = new ThreadPoolExecutor(
            minSpareThreads, maxThreads, 60, TimeUnit.SECONDS,
            taskqueue, tf);
        taskqueue.setParent((ThreadPoolExecutor) executor);
    }
}

// TaskQueue 核心：当线程数 < maxThreads 时，offer 返回 false，迫使创建新线程
public class TaskQueue extends LinkedBlockingQueue<Runnable> {
    @Override
    public boolean offer(Runnable o) {
        if (parent != null && parent.getPoolSize() == parent.getMaximumPoolSize()) {
            return super.offer(o); // 线程已满，入队
        }
        if (parent.getPoolSize() < parent.getMaximumPoolSize()) {
            return false; // 线程未满，不入队，触发创建新线程
        }
        return super.offer(o);
    }
}
```

### 8.2 线上调优实战（12年经验）

**Session 持久化方案对比**：

| 方案 | 实现 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **内存** | StandardManager | 最快 | 单机，重启丢失 | 单机开发 |

## 十二、嵌入式 Tomcat vs 独立部署 vs Jetty/Undertow 选型决策树

### 12.1 部署形态对比

| 形态 | 代表 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **独立 Tomcat** | 传统 WAR 部署 | 运维统一、多应用隔离、热部署 | 部署复杂、版本绑定 | 传统企业、多 WAR 共享容器 |
| **嵌入式 Tomcat** | Spring Boot 默认 | 开箱即用、版本随应用、云原生友好 | 每应用一个 JVM，内存占用高 | **微服务、云原生、新项目首选** |
| **Jetty** | Eclipse Jetty | 轻量、易嵌入、可定制 | 生态略逊 Tomcat | 需深度定制的嵌入式场景 |
| **Undertow** | WildFly / Spring Boot 可选 | 性能最优、非阻塞、内存占用低 | 生态小、资料少 | 极致性能、网关层 |

### 12.2 选型决策树

```
需要多应用共享容器？
  ├─ 是 → 独立 Tomcat（Host 隔离 Context）
  └─ 否 → 微服务/单应用？
           ├─ 是 → Spring Boot 嵌入式？
           │        ├─ 追求极致性能 → Undertow
           │        ├─ 追求生态成熟 → Tomcat (默认)
           │        └─ 需定制 → Jetty
           └─ 否 → 传统单体 WAR → 独立 Tomcat
```

| Tomcat 整体架构？ | 分层设计 | Coyote（连接器）+ Catalina（容器）+ Jasper（JSP），Server→Service→Engine→Host→Context→Wrapper 六层容器 |
| Connector 与 Container 区别？ | 职责分离 | Connector 管网络 I/O，Container 管业务逻辑，通过 Adapter 桥接 |
| BIO/NIO/NIO2/APR 区别？ | I/O 模型 | BIO 已废弃；NIO 默认 Selector 非阻塞；NIO2 异步；APR Native 极致性能 |
| Acceptor/Poller/Worker 作用？ | 线程模型 | Acceptor 阻塞 accept，Poller Selector 轮询，Worker 处理业务；三级解耦 |
| 如何打破双亲委派？ | 类加载隔离 | WebappClassLoader 优先加载 WEB-INF/classes 和 lib，再委托父；delegate=false 默认子优先 |
| Pipeline-Valve 是什么？ | 责任链 | 每个容器一个 Pipeline，串联 Valve，最后 BasicValve 负责分发到子容器 |
| Lifecycle 作用？ | 模板方法 | 统一组件生命周期，级联启停，状态机管理 |
| maxThreads/acceptCount/maxConnections 区别？ | 参数调优 | maxThreads 工作线程数；acceptCount 等待队列；maxConnections 最大连接数（NIO 长连接） |
| 如何调优到万级并发？ | 系统化调优 | 垂直调优（线程/JVM/内核）→ 动静分离 → 水平扩容 → 缓存 → 异步化 |
| Tomcat 内存泄漏常见原因？ | 类加载器泄漏 | ThreadLocal 未清理、JDBC 驱动未注销、非守护线程未停止，热部署时 WebappClassLoader 无法 GC |
| 嵌入式 Tomcat 与独立 Tomcat 区别？ | 部署形态 | 嵌入式随应用启动，版本隔离云原生友好；独立多应用共享容器，运维统一 |
| Tomcat vs Jetty vs Undertow？ | 选型 | Tomcat 生态最强默认选它；Undertow 性能最优适合网关；Jetty 可定制强 |
| 如何排查 Tomcat 线程阻塞？ | 线上排障 | jstack 看 catalina-exec 线程状态；重点关注 WAITING/PARKED，查 DB/Redis 慢调用 |
| keepAlive 作用与坑？ | 连接复用 | 复用 TCP 减少握手，但占用 Worker 线程，API 服务建议缩短至 5s |
| 为什么 Context reloadable 生产必须 false？ | 热部署 | 后台线程频繁扫描 + 类加载器泄漏风险 |
