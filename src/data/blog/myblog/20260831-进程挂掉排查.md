> **“进程为什么没了？” → “谁杀的？” → “为什么被杀？” → “进程死前发生了什么？” → “OS/容器/平台做了什么？”**

先给你一个总图：

```text
                    进程突然消失
                         │
             ┌───────────┴───────────┐
             │                       │
        进程主动退出              被外部杀死
             │                       │
       exit / System.exit       SIGTERM / SIGKILL
       Java异常                  OOM Killer
       shutdown                systemd
       native crash             Kubernetes
             │                   Docker
             │                   LB/平台
             │
             └───────────┬───────────┘
                         ↓
                 操作系统 / 容器
                         ↓
              JVM / Application
                         ↓
                    日志 / Dump
```

我建议你以后遇到“Java 进程突然挂了”，**严格按照下面的顺序排查**。

---

# 一、第一步：先确认“到底是死了，还是只是不可用了”

这是最容易犯的错误。

例如：

```text
用户访问不了
```

不代表：

```text
Java 进程死了
```

可能是：

```text
                    用户请求
                       │
                       ↓
                     LB
                       │
             ┌─────────┴─────────┐
             │                   │
          Gateway A           Gateway B
             │
             ↓
         Java process
```

可能只是：

* LB 健康检查失败
* 网络断了
* DNS 异常
* Java 卡死
* Full GC
* CPU 100%
* 线程池耗尽
* connection pool 耗尽
* 数据库挂了
* 进程真的退出了

所以第一步：

```bash
ps -ef | grep java
```

或者：

```bash
pgrep -af java
```

如果进程不存在：

```bash
pgrep -af java
```

没有结果。

这才进入：

> **进程死亡排查。**

---

# 二、第一大类：确认是不是 Linux OOM Kill

这是线上 Java 服务非常常见的一种。

尤其你之前就在排查 X-WRT 的：

```text
oom-killer
CrashCore
```

所以这个你应该重点掌握。

---

## 2.1 看内核日志

首先：

```bash
dmesg -T | grep -Ei "oom|out of memory|killed process|oom-killer"
```

如果是：

```text
Out of memory: Killed process 12345 (java)
```

基本就可以确认：

> Linux Kernel OOM Killer 杀了 Java。

例如：

```text
[Mon Aug 31 15:30:01 2026] Out of memory: Killed process 12345 (java)
```

继续看：

```bash
dmesg -T | grep -A 30 -B 30 "Killed process"
```

---

# 三、如果服务器使用 systemd

例如：

```bash
systemctl status my-java.service
```

重点看：

```text
Active:
Main PID:
Result:
ExecMainCode:
ExecMainStatus:
```

例如：

```text
Active: failed
Result: oom-kill
```

那就非常明确了：

```text
systemd
   ↓
Java
   ↓
OOM
```

还可以：

```bash
journalctl -u my-java.service
```

查看服务日志。

查看最近一次：

```bash
journalctl -u my-java.service -n 500
```

查看某个时间段：

```bash
journalctl -u my-java.service \
  --since "2026-08-31 15:00:00" \
  --until "2026-08-31 16:00:00"
```

---

# 四、如果怀疑是 SIGKILL / SIGTERM

Linux 进程死亡，本质上经常和：

```text
signal
```

有关。

最重要的几个：

```text
SIGTERM  15
SIGKILL   9
SIGSEGV  11
SIGABRT   6
SIGBUS    7
SIGFPE    8
```

---

# 五、SIGTERM：有人让它“优雅退出”

比如：

```bash
kill 12345
```

默认就是：

```text
SIGTERM
```

它和：

```bash
kill -15 12345
```

一样。

Java 可以处理：

```java
Runtime.getRuntime().addShutdownHook(...)
```

所以如果是 SIGTERM，通常你可能在日志里看到：

```text
Shutdown initiated
Stopping Tomcat
Closing datasource
Stopping executor
```

然后：

```text
Process exited
```

---

# 六、SIGKILL：直接弄死

如果：

```bash
kill -9 12345
```

就是：

```text
SIGKILL
```

Java：

```text
没有机会执行 shutdown hook
没有机会 finally
没有机会打印日志
没有机会生成 Java heap dump
```

所以你可能看到：

```text
application.log

15:30:00 processing request
15:30:01 processing request
15:30:01
              ← 突然没了
```

这种情况非常像：

```text
SIGKILL
```

但是：

> **仅仅看到日志突然断了，不能证明是 SIGKILL。**

还需要查外部来源。

---

# 七、查是谁发了 kill

这是非常关键的一层。

因为：

```text
Java 被 SIGKILL
```

只是结果。

真正的问题可能是：

```text
谁 kill 的？
```

可能是：

```text
管理员
systemd
Kubernetes
Docker
OOM Killer
CI/CD
部署脚本
watchdog
supervisor
平台
其他程序
```

---

# 八、Linux 审计：查是谁调用 kill

如果机器开启了 auditd，可以查：

```bash
ausearch -sc kill
```

或者：

```bash
ausearch -m SIGNAL
```

也可以：

```bash
auditctl -l
```

如果配置了进程/信号审计，可以看到：

```text
who
pid
uid
exe
signal
```

这对于：

> “到底谁 kill 我的 Java？”

非常有价值。

但要注意：

**如果事先没有配置相关 audit 规则，事故发生后未必能补回来。**

所以生产环境最好提前规划。

---

# 九、检查 shell / cron / 脚本

很多“神秘进程死亡”最后发现是：

```text
crontab
```

或者：

```text
部署脚本
监控脚本
watchdog
```

执行：

```bash
crontab -l
```

系统级：

```bash
cat /etc/crontab
ls -l /etc/cron.*
```

搜索：

```bash
grep -R "kill.*java" /etc /opt /usr/local 2>/dev/null
```

也可以：

```bash
grep -R "pkill\|killall\|kill -9" \
    /etc /opt /usr/local 2>/dev/null
```

# 十、检查 systemd 是否杀了它

例如：

```bash
systemctl cat my-java.service
```

重点看：

```text
Restart=
RestartSec=
TimeoutStopSec=
KillMode=
WatchdogSec=
OOMPolicy=
MemoryMax=
MemoryHigh=
```

特别注意：

```text
MemoryMax=
```

例如：

```ini
[Service]
MemoryMax=4G
```

那么：

```text
Java
 ↓
超过 cgroup memory limit
 ↓
OOM
 ↓
被杀
```

# 十一、如果运行在 Docker

首先：

```bash
docker ps -a
```

然后：

```bash
docker inspect <container>
```

重点：

```bash
docker inspect <container> \
  --format '{{.State.Status}} {{.State.ExitCode}} {{.State.OOMKilled}}'
```

例如：

```text
exited 137 true
```

这非常重要。

---

# 十二、Docker Exit Code 要记住

常见：

```text
0
```

正常退出。

```text
1
```

普通错误。

```text
137
```

非常值得警惕：

```text
128 + 9
```

即：

```text
SIGKILL
```

通常：

```text
OOM
```

但不要机械地认为：

> 137 = 一定 OOM。

还需要：

```bash
docker inspect
```

看：

```text
OOMKilled
```

---

# 十三、Kubernetes 环境更加重要

如果 Java 在 Kubernetes：

```bash
kubectl get pod
```

然后：

```bash
kubectl describe pod <pod>
```

重点看：

```text
State
Last State
Reason
Exit Code
Signal
Restart Count
Events
```

例如：

```text
Last State:
  Terminated
    Reason: OOMKilled
    Exit Code: 137
```

那么：

```text
Kubernetes / cgroup
        ↓
Memory limit
        ↓
OOM
        ↓
Java killed
```

---

# 十四、Kubernetes 一定要看 Events

```bash
kubectl get events \
  --sort-by='.lastTimestamp'
```

或者：

```bash
kubectl describe pod xxx
```

最下面：

```text
Events:
```

经常会出现：

```text
Killing container
Back-off restarting failed container
Liveness probe failed
Readiness probe failed
```

---

# 十五、特别注意 Liveness Probe

这个非常容易被误判。

例如：

```text
Java
 ↓
Full GC
 ↓
10 秒没有响应
 ↓
Kubernetes liveness probe
 ↓
失败
 ↓
Kubernetes restart
```

最终你看到：

```text
Java进程没了
```

实际上不是：

```text
Java自己崩了
```

而是：

```text
Kubernetes把它杀了。
```

---

# 十六、检查 Java 自己是不是异常退出

如果 Java 进程：

```text
Exception
```

导致退出，需要看：

```text
stdout
stderr
application.log
```

例如：

```text
Exception in thread "main"
java.lang.OutOfMemoryError
```

注意这里有两种完全不同的 OOM：

### JVM OOM

```text
java.lang.OutOfMemoryError: Java heap space
```

这是：

```text
JVM自己发现堆不够
```

### Linux OOM Killer

```text
Out of memory: Killed process xxx (java)
```

这是：

```text
Linux Kernel
```

两个一定要区分。

---

# 十七、Java OOM 要看具体是哪一种

常见：

```text
Java heap space
```

说明：

```text
Heap
```

不足。

---

```text
GC overhead limit exceeded
```

说明：

```text
GC 花大量时间
但是回收效果非常差
```

---

```text
Direct buffer memory
```

说明：

```text
Direct Memory
```

不足。

Netty 特别常见。

---

```text
unable to create native thread
```

说明：

```text
线程创建失败
```

可能是：

```text
线程数量
进程限制
内存
PID limit
```

---

```text
OutOfMemoryError: Metaspace
```

说明：

```text
Metaspace
```

不足。

---

# 十八、检查 Java 是否产生 Heap Dump

如果配置了：

```bash
-XX:+HeapDumpOnOutOfMemoryError
```

那么 OOM 后可能出现：

```text
java_pid1234.hprof
```

搜索：

```bash
find / -name "*.hprof" 2>/dev/null
```

然后用：

```text
Eclipse MAT
VisualVM
JProfiler
```

分析。

---

# 十九、检查 JVM Crash：hs_err_pid

这是 Java Native Crash 最重要的东西之一。

例如：

```text
hs_err_pid12345.log
```

搜索：

```bash
find / -name "hs_err_pid*.log" 2>/dev/null
```

如果看到：

```text
A fatal error has been detected by the Java Runtime Environment
```

例如：

```text
SIGSEGV (0xb)
```

那不是普通 Java exception。

而是：

```text
JVM / native library
```

崩了。

---

# 二十、典型的 JVM Crash 原因

例如：

```text
JNI
Netty native
libc
glibc
OpenSSL
jemalloc
GPU library
JDK bug
第三方 native library
```

这时候重点看：

```text
# A fatal error has been detected
# SIGSEGV
# Problematic frame:
```

比如：

```text
Problematic frame:

C  [libxxx.so+0x1234]
```

那么就应该重点查：

```text
libxxx.so
```

而不是继续查 Java Heap。

# 二十一、看 Core Dump

Linux 可以产生：

```text
core
```

检查：

```bash
ulimit -c
```

如果：

```text
0
```

表示 core dump 被禁用了。

可以检查：

```bash
cat /proc/sys/kernel/core_pattern
```

例如：

```text
core
```

或者：

```text
|/usr/lib/systemd/systemd-coredump
```

---

# 二十二、systemd-coredump

如果系统启用了：

```text
systemd-coredump
```

可以：

```bash
coredumpctl list
```

然后：

```bash
coredumpctl info
```

或者：

```bash
coredumpctl info <PID>
```

甚至：

```bash
coredumpctl debug <PID>
```

进入：

```text
gdb
```

分析。

# 二十三、如果是 SIGSEGV，重点看 core

比如：

```bash
gdb /path/to/java core
```

然后：

```gdb
bt
```

看：

```text
backtrace
```

进一步：

```gdb
thread apply all bt
```

查看所有 native thread。

这个对：

```text
C/C++
JNI
JVM
native library
```

特别重要。

---

# 二十四、检查内核是不是发生了 Panic

如果不是单个 Java 死了，而是：

```text
整个机器突然重启
```

就不能只看 Java。

检查：

```bash
journalctl -k -b -1
```

这里：

```text
-b -1
```

表示：

> 上一次 boot。

非常重要。

---

# 二十五、看上一次系统为什么重启

```bash
last reboot
```

以及：

```bash
journalctl --list-boots
```

例如：

```text
-1
  2026-08-31 ...
  0
  2026-08-31 ...
```

然后：

```bash
journalctl -b -1
```

---

# 二十六、如果机器突然断电

这种情况：

```text
Java
 ↓
突然没了
```

但：

```text
整个服务器
```

都重启了。

你应该查：

```bash
last -x
```

以及：

```bash
journalctl -b -1 -e
```

如果最后日志突然断掉：

```text
15:30:00 ...
15:30:01 ...
```

然后下一次：

```text
system boot
```

可能是：

```text
断电
硬件复位
kernel panic
hypervisor reset
```

# 二十七、检查硬件错误

如果怀疑硬件：

```bash
dmesg -T | grep -Ei \
"mce|machine check|hardware error|edac|ecc"
```

CPU：

```text
Machine Check Exception
```

内存：

```text
EDAC
ECC
```

也可以：

```bash
journalctl -k | grep -Ei "hardware|mce|edac|ecc"
```

# 二十八、检查磁盘

磁盘异常也可能导致 Java：

```text
卡死
退出
启动失败
日志无法写入
```

检查：

```bash
dmesg -T | grep -Ei \
"error|i/o|nvme|ext4|xfs"
```

SSD：

```bash
smartctl -a /dev/nvme0
```

NVMe：

```bash
nvme smart-log /dev/nvme0
```

# 二十九、检查磁盘是不是满了

非常常见。

```bash
df -h
```

以及：

```bash
df -i
```

注意：

```text
磁盘空间满
```

和：

```text
inode 满
```

是两个问题。

例如：

```text
df -h
```

还有空间，但是：

```text
df -i
```

100%。

一样无法创建文件。

# 三十、检查文件句柄

Java 服务可能因为：

```text
Too many open files
```

出问题。

查看：

```bash
ulimit -n
```

当前进程：

```bash
cat /proc/<pid>/limits
```

重点：

```text
Max open files
Max processes
```

# 三十一、查看进程到底打开了多少 FD

```bash
ls /proc/<pid>/fd | wc -l
```

或者：

```bash

```

查看：

```bash
lsof -p <pid>
```

非常有用。

# 三十二、检查线程数量

```bash
ps -eLf | grep <pid> | wc -l
```

或者：

```bash
ls /proc/<pid>/task | wc -l
```

如果线程数量非常高：

```text
5000
10000
```

就需要高度怀疑：

```text
thread leak
线程池配置
native thread
```

---

# 三十三、检查进程限制

```bash
cat /proc/<pid>/limits
```

非常值得看。

例如：

```text
Max processes
Max open files
Max locked memory
Max address space
Max stack size
```

# 三十四、检查 CPU 是否打满

进程死亡前：

```bash
top
```

或者：

```bash
pidstat -p <pid> 1
```

重点：

```text
%CPU
```

如果：

```text
800%
```

说明多核 CPU 被大量占用。

进一步：

```bash
pidstat -t -p <pid> 1
```

看具体线程。

Java：

```bash
top -H -p <pid>
```

找到：

```text
TID
```

然后：

```bash
printf '%x\n' <TID>
```

转换成十六进制：

```text
nid
```

再去：

```text
jstack
```

找对应线程。

---

# 三十五、检查内存到底是谁吃掉的

不要只看：

```bash
free -h
```

还要：

```bash
ps aux --sort=-%mem | head
```

以及：

```bash
smem
```

如果有。

Java：

```bash
jcmd <pid> VM.native_memory summary
```

前提：

```text
-XX:NativeMemoryTracking=summary
```

---

# 三十六、Java 内存一定要分层看

这是高级 Java 排障必须掌握的：

```text
Java Process
│
├── Java Heap
│    ├── Young
│    └── Old
│
├── Metaspace
│
├── Code Cache
│
├── Thread Stack
│
├── Direct Memory
│
├── JNI
│
├── GC
│
└── Native Memory
```

所以：

```text
-Xmx 8G
```

不代表：

```text
Java进程最多只需要8G。
```

完全可能：

```text
-Xmx = 8G
RSS = 12G
```

甚至更多。

---

# 三十七、为什么 Linux OOM 会杀 Java？

比如：

```text
物理内存
32GB
```

Java：

```text
-Xmx 20G
```

但：

```text
Heap        20G
Direct       4G
Metaspace    1G
Thread       2G
Native       2G
Page Cache   ...
```

最终：

```text
系统内存耗尽
```

Linux：

```text
OOM Killer
   ↓
选择 victim
   ↓
SIGKILL
   ↓
Java死亡
```

所以：

> **Java 没有 `OutOfMemoryError`，也完全可能是 OOM。**

因为是 Linux 杀的。

---

# 三十八、检查 OOM Killer 为什么选择这个进程

Linux 有：

```text
oom_score
oom_score_adj
```

查看：

```bash
cat /proc/<pid>/oom_score
cat /proc/<pid>/oom_score_adj
```

例如：

```text
oom_score = 900
```

说明这个进程在 OOM 情况下比较容易成为 victim。

---

# 三十九、检查 cgroup memory

现代 Linux 很重要。

如果使用 cgroup：

```bash
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.max
```

cgroup v2 下还可以：

```bash
cat /sys/fs/cgroup/memory.events
```

重点：

```text
oom
oom_kill
```

例如：

```text
oom 5
oom_kill 1
```

这几乎就是铁证。

---

# 四十、如果是 Java 服务，我建议你建立“事故证据链”

真正专业的排查不是：

```text
看一个日志
```

而是：

```text
             Java 消失
                 │
                 ▼
        ① PID 是否存在？
                 │
                 ▼
        ② systemd / Docker / K8s
                 │
                 ▼
        ③ Exit Code / Signal
                 │
                 ▼
        ④ Kernel 日志
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
       OOM      Crash     Panic
        │        │        │
        ▼        ▼        ▼
      cgroup    hs_err    journal
      dmesg     core      previous boot
                 │
                 ▼
        ⑤ JVM 日志 / GC 日志
                 │
                 ▼
        ⑥ Application Log
                 │
                 ▼
        ⑦ 外部系统
        LB / K8s / systemd
        watchdog / deploy
```

# 四十一、我给你一套“进程突然死亡”的标准命令清单

假设：

```text
Java PID = 12345
服务 = my-java
```

### 第一轮：5分钟快速判断

```bash
ps -p 12345 -f

dmesg -T | tail -200

dmesg -T | grep -Ei \
"oom|killed process|segfault|general protection|panic"

journalctl -u my-java -n 300

systemctl status my-java

coredumpctl list
```

# 四十五、最重要的一张“死亡原因对照表”

| 现象                    | 高概率原因                           | 第一检查点              |
| --------------------- | ------------------------------- | ------------------ |
| `OutOfMemoryError`    | JVM OOM                         | Java 日志            |
| `Killed process java` | Linux OOM                       | `dmesg`            |
| Exit 137              | SIGKILL                         | Docker/K8s/cgroup  |
| Exit 143              | SIGTERM                         | systemd/K8s/人为     |
| `SIGSEGV`             | Native/JVM crash                | `hs_err_pid`       |
| `SIGABRT`             | native abort                    | core / hs_err      |
| `core dumped`         | native crash                    | `coredumpctl`      |
| 进程突然消失                | SIGKILL/OS OOM                  | kernel + audit     |
| 日志突然断                 | kill -9 / crash / machine issue | kernel             |
| Java 消失但机器没重启         | process-level issue             | systemd/kernel     |
| 所有服务一起消失              | OS/hardware                     | kernel/boot        |
| 机器突然重启                | panic/power/hypervisor          | `journalctl -b -1` |
| Pod 重启                | K8s                             | `describe pod`     |
| Container 重启          | Docker/systemd                  | `inspect`          |
| 端口消失                  | process/socket exit             | `ss -lntp`         |
| 端口还在但服务不可用            | 卡死/网络/线程池                       | `ss` + `jstack`    |
| CPU 100% 后死亡          | OOM/watchdog/native             | kernel + JVM       |
| Full GC 后死亡           | JVM OOM / watchdog              | GC log + K8s       |
| FD 爆满                 | FD leak                         | `lsof`             |
| 线程爆满                  | thread leak                     | `/proc/<pid>/task` |

# 四十六、还有一个非常关键的问题：不要等死了才排查

这是生产环境最容易犯的错误。

如果：

```text
Java PID = 12345
```

进程已经死了，再执行：

```bash
jstack 12345
jmap 12345
jcmd 12345
```

已经没用了。

所以生产环境真正应该做的是：

```text
               Java运行中
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      Metrics     Logs       Dumps
        │          │          │
        ↓          ↓          ↓
      CPU/RSS     GC         Heap
      Threads     Error      Core
      FD          Access     hs_err
```

提前把**证据留存下来**。

尤其建议：

```text
1. GC Log
2. JVM 启动参数
3. stdout/stderr
4. application log
5. systemd journal
6. kernel journal
7. cgroup memory.events
8. hs_err_pid
9. core dump
10. Prometheus/Grafana 指标
11. Kubernetes events
12. 部署记录
```

# 四十七、如果让我给你设计一套 Java 线上“进程死亡诊断体系”

我会做成下面这样：

```text
                    ┌───────────────┐
                    │ Java Process  │
                    └───────┬───────┘
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
       JVM层              OS层             平台层
          │                 │                 │
     GC Log             dmesg             K8s
     Heap Dump          journalctl        Docker
     hs_err             cgroup           systemd
     JFR                core             LB
     jstack             audit            watchdog
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ▼
                    Death Analyzer
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
          OOM Kill       Crash          Graceful
             │              │              │
          cgroup         SIGSEGV        SIGTERM
          memory         native         exit()
          kernel         JVM            deploy
```
