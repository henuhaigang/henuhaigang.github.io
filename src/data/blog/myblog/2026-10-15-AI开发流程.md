你这个问题，其实是 AI 辅助开发中非常关键的一步：你有一个产品想法，但不知道怎么把想法变成产品需求、页面原型、技术方案，最后变成真正能运行的 App。

你不需要先学会画原型图，也不需要一开始就知道应该使用什么技术栈。你真正需要的是一套能把“模糊想法”逐步转化为“可开发、可验证产品”的方法，以及一套能让编程 Agent 按照这个方法工作的提示词和 Skills。

考虑到你使用 Claude Code CLI、OpenCode 等编程 Agent，我建议你建立一套可以在不同项目中复用的 AI 产品开发工作流。

## 一、先建立正确的开发思维：不要从写代码开始

假设你只有一个简单想法：

> 我想做一个帮助用户进行日常训练的 App，能够记录训练情况，提醒用户每天训练，并查看训练进度。

这时，你还不知道应该有哪些页面、按钮放在哪里、数据怎么保存，甚至不知道应该用什么技术。

这完全正常。合理的开发流程应该是：

第 1 步：描述想法

我想解决什么问题？谁会使用？

第 2 步：产品需求分析

用户是谁、有哪些场景、第一版做什么？

第 3 步：页面设计与原型

有哪些页面？用户如何操作？

第 4 步：技术方案与任务拆分

技术栈、数据模型、接口、开发顺序

第 5 步：Agent 分阶段实现

先做可运行版本，再逐步增加功能

第 6 步：运行、测试、验收

启动 App、实际体验、发现问题、迭代

你需要做的不是一次性把所有需求想清楚，而是让大模型在每一个阶段帮助你补齐缺失的信息，并在关键节点让你确认方向。

最重要的原则：先确定做什么，再决定怎么做，最后才是怎么写代码。

## 二、不会画原型图怎么办？让大模型先帮你设计，再生成可交互原型

你不需要自己画图。你可以用自然语言描述需求，让大模型负责以下工作：

- 识别用户需要哪些功能。
- 推导需要哪些页面。
- 设计每个页面的信息层级和操作流程。
- 提出合理的布局方案。
- 生成页面原型。
- 根据你的反馈调整布局。

而且，原型图不一定要是图片。

我更推荐你采用这个顺序：

1. 先让大模型用文字列出页面及其功能。
2. 再生成低保真原型，确认布局和交互。
3. 确认后生成高保真设计或直接实现可交互页面。
4. 最后接入真实数据、接口和业务逻辑。

这样可以避免花费大量时间生成一套漂亮、但不符合实际需求的 UI。

## 三、你真正需要的是一套固定的提示词，而不是一句万能提示词

建议你把和大模型的对话分成几个阶段。每个阶段有明确的输入、输出和验收标准。

### 阶段 1：把一个模糊想法变成产品需求

你最初甚至只需要说：

> 我想做一个 App，主要帮助用户完成某项任务。我不懂产品设计，也不会画原型。你先不要写代码，请像一位资深产品经理一样，通过对话帮我梳理需求，逐步形成一个可以开发的产品方案。

接下来使用下面这份提示词。

```

# 角色

你是一名资深产品经理、UX 设计师和技术产品顾问。

我只有一个初步想法，不一定能完整表达需求，
也不一定知道正确的功能和交互方式。

# 你的任务

帮助我把模糊想法转化为清晰、可开发的产品需求。

# 工作规则

1. 不要假设我已经知道所有需求。
2. 不要一上来就问几十个问题。
3. 每轮优先询问最重要的 1～3 个问题。
4. 如果信息不足，可以先提出合理假设，并明确标注。
5. 对于我没有想到的功能，主动提出建议，并解释原因。
6. 区分第一版必需功能、后续增强功能和暂时不做的功能。
7. 不要在需求尚未明确时直接生成代码。

# 工作步骤

第一步：理解产品想法
- 解决什么问题？
- 目标用户是谁？
- 用户在什么场景下使用？
- 产品的核心价值是什么？

第二步：梳理用户场景
- 用户如何开始使用？
- 用户需要完成哪些任务？
- 正常流程、异常流程分别是什么？

第三步：设计功能范围
- 核心功能清单
- 功能优先级
- 第一版 MVP 范围
- 暂不实现的功能

第四步：形成产品需求文档
- 产品目标
- 用户角色
- 用户故事
- 功能需求
- 业务规则
- 异常场景
- 验收标准

# 每个阶段的输出要求

用通俗易懂的语言解释你的判断。
列出需要我确认的事项。
允许我随时修改之前的决定。

只有在需求足够清楚后，才进入下一阶段。
最终输出结构化 PRD，并标记尚未确定的内容。

```

为什么要这么写？

因为你不应该承担“想清楚所有功能”的责任。你只需要描述问题，大模型负责提出问题、发现遗漏、整理方案；但涉及产品方向和业务取舍时，最终仍由你确认。

### 阶段 2：让大模型从 PRD 推导页面

当 PRD 基本确定后，不要马上让它写前端代码。先让它设计页面。

```

你现在是一名资深 UX/UI 设计师。

请根据已经确认的 PRD，设计这个 App 的完整页面结构和交互流程。

要求：

1. 先分析用户需要完成的核心任务。
2. 列出页面清单，并解释每个页面的作用。
3. 设计页面之间的跳转关系。
4. 逐个页面描述布局、组件、按钮和交互。
5. 为每个页面补充加载中、空数据、错误、成功等状态。
6. 明确底部导航、顶部导航、弹窗、表单和返回行为。
7. 检查页面之间是否存在功能遗漏或操作断点。

不要直接编写正式业务代码。

先输出：
- 页面清单
- 页面关系图
- 核心用户流程
- 每个页面的线框布局说明

然后生成可预览的低保真原型。

如果无法直接生成可交互原型，请使用 HTML/CSS/JavaScript
生成一个可在浏览器打开的独立原型页面。

原型中的按钮应尽可能可以实际点击，
以便我体验主要操作流程。

最后告诉我：
- 哪些设计需要我确认
- 哪些地方存在不确定性
- 下一步应该先验证什么

```

这里我特别建议你要求生成可点击的 HTML 原型。它比一张静态图片更适合不会画原型的开发者，因为你可以直接点击按钮、切换页面、填写表单，判断产品操作起来是否符合预期。

### 阶段 3：让大模型把设计转成技术方案

等你确认页面和主要流程后，再使用：

```

你现在是一名资深软件架构师。

请基于已经确认的 PRD、页面原型和交互流程，
设计本项目的技术实现方案。

要求：

1. 先检查需求、页面和业务规则是否一致。
2. 推荐合适的技术栈，并解释选择依据。
3. 明确前端、后端、数据库、外部服务的边界。
4. 设计核心数据模型和表结构。
5. 设计 API 或本地数据访问接口。
6. 分析身份认证、权限、数据安全和错误处理。
7. 识别关键技术风险、依赖和需要验证的假设。
8. 设计测试方案和可验证的验收标准。
9. 将项目拆分为可以独立实现和验收的小任务。
10. 标明任务依赖关系，避免一次生成整个项目。

请输出：
- 技术架构图
- 项目目录结构
- 核心数据模型
- API 设计
- 任务依赖图
- 分阶段实施计划
- 每个任务的验收标准

不要在我确认技术方案之前开始正式实现。
如果存在更简单的方案，优先考虑满足需求的最小复杂度。

```

这里还有一个很重要的原则：让大模型先给出推荐方案和理由，不要要求它把所有可能的技术方案都列出来后再让你自己选择。 你可以指出限制条件，由它给出一个主推方案及备选方案。

## 四、如果你用 Claude Code 或 OpenCode，应该怎么设计 Skills？

上面几份提示词适合你在聊天中逐阶段使用。但如果每次开发 App 都要重新复制这些提示词，会很麻烦。

更好的办法是：把这些方法沉淀成一套可复用的项目开发 Skills，让 Agent 知道每个阶段应该做什么、产出什么，以及什么时候可以进入下一阶段。

我建议先设计一个主流程 Skill，再按职责拆分子 Skill。

app-development-workflow

总控流程：根据当前项目阶段，调用对应能力

product-discovery

需求澄清、MVP、PRD

ui-prototyping

页面清单、线框图、可点击原型

architecture-design

技术选型、数据模型、接口

implementation-planning

任务拆分、依赖、验收条件

implementation

分阶段编码、测试、代码审查

run-and-verify

启动服务、健康检查、验收

### 建议的目录结构

```
your-project/
├── AGENTS.md
├── CLAUDE.md
├── .claude/
│   └── skills/
│       ├── app-development-workflow/
│       │   └── SKILL.md
│       ├── product-discovery/
│       │   └── SKILL.md
│       ├── ui-prototyping/
│       │   └── SKILL.md
│       ├── architecture-design/
│       │   └── SKILL.md
│       ├── implementation-planning/
│       │   └── SKILL.md
│       └── run-and-verify/
│           └── SKILL.md
├── docs/
│   ├── product/
│   │   └── PRD.md
│   ├── design/
│   │   ├── pages.md
│   │   └── prototype/
│   ├── architecture/
│   │   └── architecture.md
│   └── development/
│       └── tasks.md
├── scripts/
│   └── dev.sh
└── src/
```

这是一个逻辑示例，不是所有 Agent 都能直接识别的通用目录。比如 Claude Code 有自己的项目级 Skill 目录规范；OpenCode 应按照其当前版本的 Skill 发现规则配置。`AGENTS.md`、`CLAUDE.md` 也不应该不加区分地复制全部内容。

如果你希望私有 Skills 存放在独立仓库，可以把技能仓库放在项目外，通过符号链接、安装脚本或工具支持的技能搜索路径引入。这样每个项目可以使用同一套开发方法，又不必把所有技能正文提交到项目代码仓库。

### 主流程 Skill 应该写什么？

它不应该重复所有产品设计知识，而应该负责流程控制。

```

---
name: app-development-workflow
description: Guide an app from an initial vague idea through
  requirements, prototype, architecture, implementation,
  and runtime verification.
---

# App Development Workflow

## Goal

Turn an initial product idea into a working, tested application
through explicit, reviewable stages.

## Stages

1. Discovery
2. Requirements
3. UI and interaction prototype
4. Architecture
5. Implementation planning
6. Incremental implementation
7. Testing and runtime verification
8. Acceptance and iteration

## Rules

- Identify the current project stage before acting.
- Load only the skills needed for the current stage.
- Preserve confirmed decisions and document assumptions.
- Ask a small number of high-value questions at a time.
- Never invent user approval for a major product decision.
- Do not skip prototype review when the UI is still uncertain.
- Do not implement the whole app in one uncontrolled operation.
- Keep project documentation synchronized with approved changes.
- Run tests and verify runtime behavior after implementation.
- Report failures honestly.

## Stage Transitions

Do not advance past a major decision point without checking
whether its required outputs exist and are sufficiently complete.

Allow the user to revise earlier decisions.
When requirements change, identify affected designs, tasks and code.

## Final Result

The application must be runnable, its core user journey must work,
and its implementation must satisfy the agreed acceptance criteria.

```

这套主流程的价值在于：以后你只需要对 Agent 说“我要做一个 App”，它就能先进入需求梳理，而不是一上来创建几十个源代码文件。

## 五、如何避免 Agent 一次生成整个 App，最后却不能用？

这是整个流程里最值得注意的部分。

建议把每个阶段的产出定义为交付物 + 验收标准，而不是只给 Agent 一个任务名称。

| 阶段   | 必须产出的内容         | 进入下一阶段的条件   |
| ---- | --------------- | ----------- |
| 产品需求 | PRD、用户场景、MVP 范围 | 核心需求与业务规则明确 |
| 页面设计 | 页面清单、流程图、原型     | 核心操作流程得到确认  |
| 技术设计 | 架构、数据模型、接口      | 技术方案满足产品需求  |
| 任务规划 | 有依赖关系的任务清单      | 每个任务有明确验收条件 |
| 开发实现 | 代码、测试、构建结果      | 当前任务通过验收    |
| 运行验证 | 运行状态、健康检查、日志    | 核心流程实际可用    |

例如，不要给 Agent 这样的任务：

> 开发一个完整的训练 App，要求功能齐全、界面漂亮。

改成：

> 根据已经确认的 PRD，先实现首页和训练详情页。使用本地模拟数据，暂时不接入后端。完成后启动应用，验证页面跳转、训练开始与结束流程，并列出尚未实现的功能。未经确认不要扩大任务范围。

第二种提示词更容易获得可靠结果，因为它限制了当前工作范围，并明确了完成的标准。

## 六、给你一份真正日常使用的“开工提示词”

上面的 Skill 是开发方法的长期沉淀。你每次开始一个新项目时，其实不需要重新输入所有规则。

你可以只提供下面这段提示词，再用自己的语言描述想法。

```

我想开发一个 App。

我的想法是：
【在这里用自己的话描述，不需要专业术语，不需要完整需求】

请使用 app-development-workflow 帮助我推进项目。

我的要求：

1. 我可能不知道应该有哪些功能，也不会画原型图。
   请帮助我发现遗漏，而不是要求我自己设计所有细节。

2. 先帮助我理解和完善产品需求，再进行页面设计，
   然后做技术设计，最后才进入编码。

3. 每个阶段都要有明确的交付物和验收标准。
   需要我决定的关键事项，请用通俗的语言解释。

4. 不要一次问我太多问题。
   每次优先问最影响产品方向的问题。
   如果可以合理假设，就先提出方案并标记假设。

5. 页面设计阶段，主动生成页面清单、操作流程、
   低保真原型和可点击的交互演示。
   不要只用文字描述页面。

6. 技术选型时，先根据产品需求推荐合适方案，
   不要默认引入复杂架构。

7. 开发时拆分为小任务，每完成一个阶段就进行测试、
   启动验证和结果汇报。

8. 需求、原型和技术方案发生变化时，
   检查之前的文档、任务和代码是否需要同步修改。

9. 未经我确认，不要擅自扩大 MVP 范围，
   不要执行破坏性操作或发布生产环境。

现在先进入需求探索阶段。
请先用自己的话复述你理解的产品想法，
指出最重要的未知事项，并向我提出第一轮问题。
暂时不要写代码。

```

这段提示词最适合用作新项目的入口。真正长期复用时，把它放进你的主流程 Skill，再让各个子 Skill 分别负责 PRD、原型、架构、实现和验证。

## 七、最后一个建议：让大模型承担你不熟悉的工作，但不要让它替你做所有决定

你不需要先成为产品经理、UI 设计师、架构师，才能开始开发 App。

你只需要掌握三个动作：

- 描述： 我想解决什么问题，谁会使用。
- 判断： 大模型提出的方案是否符合我的实际想法。
- 验收： 我能不能通过原型或真实运行的 App 完成目标任务。

其余部分可以让 Agent 分阶段完成。尤其是原型，你可以先看它生成的页面，再通过“这个按钮应该放在下面”“这个流程太复杂了”“我希望用户打开 App 就能看到今天的任务”这样的自然语言不断调整。

你最终要建立的不是一堆孤立的提示词，而是一套可以反复执行、能够检查结果、允许修改方向的产品开发流程。

## 关于技术选型

我的建议是：不要因为自己擅长 Java，就把所有 App 都做成 Java；也不要因为大模型会写 Rust、Swift、Kotlin，就贸然选择自己完全不熟悉的技术栈。应该优先选择“你能够驾驭、AI 能够高效实现、产品能够顺利交付”的方案。

你有多年 Java、JavaScript 和后端开发经验，这是很大的优势。你已经理解业务建模、数据库、接口设计、并发、系统架构和工程化。开发 App 时，真正需要补齐的通常是客户端 UI、交互规范、平台能力和发布流程，而不是从零学习所有软件工程知识。

因此，我建议你建立一套以产品需求为起点、以已有能力为基础、以 AI 辅助开发为加速器的技术选型方法，并将它写进前面那套 App 开发 Skills 中。

## 一、先建立一个核心原则：选产品技术栈，而不是选最喜欢的语言

技术选型时，建议优先回答下面四个问题：

1. 产品运行在哪里？ 浏览器、iPhone、Android、macOS，还是多个平台？
2. 它需要哪些平台能力？ 摄像头、蓝牙、系统通知、后台任务、文件访问、系统级集成等。
3. 你能否维护它？ 不只是让 AI 写出代码，还包括调试、升级、部署和解决线上问题。
4. AI 能否稳定完成整个交付链条？ 包括 UI、业务逻辑、测试、构建、启动、签名和发布，而不只是生成源代码。

这四个问题的优先级通常高于“哪种语言性能最好”。

例如：

- 一个 CRUD 管理后台，使用 Rust 重写后端通常不会带来足够的收益。
- 一个需要深度集成 macOS 系统能力的桌面应用，纯网页技术未必是最佳选择。
- 一个需要同时覆盖 iOS 和 Android 的普通业务 App，跨平台框架往往比维护两套原生代码更经济。

## 三、建立一张技术选型决策表：以后每个项目都按它选

先看产品需求，再确定候选方案。下面是针对个人开发、AI 辅助编码场景的初始决策表。

| 产品类型                 | 首选候选方案                           | 何时考虑其他方案                              |
| -------------------- | -------------------------------- | ------------------------------------- |
| 管理后台、运营平台、数据管理       | React + TypeScript + Spring Boot | 极简单页面可先用更轻量的前端                        |
| 个人效率工具、内容工具          | Web App / PWA                    | 需要系统集成时考虑桌面或原生 App                    |
| iOS + Android 业务 App | Flutter + Spring Boot            | 团队已有 React Native 经验时可考虑 React Native |
| macOS 桌面工具           | Tauri + Web 前端                   | 深度原生集成时考虑 Swift                       |
| Windows + macOS 桌面工具 | Tauri 或 Electron                 | 对系统集成要求高时评估原生实现                       |
| iOS 原生应用             | Swift + SwiftUI                  | 产品需要深度平台能力或原生体验                       |
| Android 原生应用         | Kotlin + Jetpack Compose         | 对 Android 平台深度集成有要求                   |
| 本地 AI / 文件处理 / 系统工具  | 按运行平台选择，业务逻辑可独立成模块               | Rust 适合特定系统级需求，但不必默认采用                |
| 高并发后端、业务 API         | Java + Spring Boot               | 出现明确的性能、资源或生态需求时再评估其他语言               |

注意两个常见误区：

- 跨平台不等于零平台知识。 Flutter、React Native、Tauri 都可能涉及原生插件、签名、权限和系统 API。
- 全栈不等于所有代码必须使用同一种语言。 完全可以用 Java 写业务后端，用 TypeScript 写前端，只有在确实需要时才引入 Rust。

## 四、技术选型时，必须把“开发成本”算进去

很多大模型会根据技术流行度、性能或者架构优雅程度推荐技术，却忽略你实际需要付出的学习和维护成本。

我建议每次都从以下六个维度进行评分。

产品需求匹配度

30%

是否支持必需的平台能力和核心功能

个人技术熟悉度

25%

你能否理解、调试和维护生成的代码

AI 编码适配度

15%

工具链成熟度、可测试性、文档质量和 Agent 工作流

开发与交付成本

15%

从原型、构建到签名、部署的总成本

生态与长期维护

10%

依赖、升级、社区、稳定性和招聘难度

性能与资源成本

5%

只有在产品有明确要求时才提高权重

这组权重是个人开发场景下的起始建议，不是通用行业标准。比如一个依赖蓝牙、后台运行的 App，平台能力和系统集成就应该占更高权重。

还要加一条硬规则：如果某个候选方案无法满足一项不可妥协的需求，就不能靠其他维度的高分把它选出来。

### 举个例子

假设你想做一个 macOS 文件处理工具，候选方案是：

- Electron + TypeScript
- Tauri + TypeScript + Rust
- Swift + SwiftUI

不要直接问大模型“哪个最好”，而是让它分别估算：

1. 完成一个可用 MVP 的难度。
2. 系统文件访问、权限和打包签名的复杂度。
3. 你需要掌握多少新知识。
4. AI 生成的代码出错后，你能否定位。
5. 未来增加功能时，架构是否容易扩展。

如果只是一个以文件上传、表单、数据展示为主的桌面工具，Tauri 或 Electron 都值得考虑；如果要深度集成 macOS 特有能力，Swift 可能更合适。最终应以具体需求做一个小型技术验证，而不是仅凭技术名称决定。

## 五、最重要的部分：把技术选型变成一个 Skill

我建议在你之前的 `app-development-workflow` 体系里，再增加一个专门的 Skill：`technology-selection`。

它的职责不是罗列所有框架，而是根据产品需求，给出有依据、可验证、适合你的技术选择。

建议目录：

```
skills/
└── technology-selection/
    ├── SKILL.md
    ├── decision-matrix.md
    ├── platform-capabilities.md
    └── validation-checklist.md
```

其中：

- `SKILL.md`：规定如何做技术选型。
- `decision-matrix.md`：记录不同产品类型的默认候选方案。
- `platform-capabilities.md`：整理 iOS、Android、macOS、Web 的平台限制。
- `validation-checklist.md`：检查技术方案是否能真正构建、运行和发布。

下面这份 `SKILL.md` 可以直接作为第一版使用。

```

---
name: technology-selection
description: Select an appropriate technology stack for a new
  application based on product requirements, developer experience,
  AI-assisted implementation, platform constraints and maintenance cost.
---

# Technology Selection Skill

## Role

Act as a senior software architect and technology advisor.

The user may have strong experience in one technology stack
but limited experience in client development or other languages.

Do not assume the user already knows the available frameworks.

## Objectives

Recommend a technology stack that:

1. Satisfies the product's functional requirements.
2. Minimizes unnecessary learning and maintenance costs.
3. Works well with AI-assisted development.
4. Supports the required deployment and distribution platforms.
5. Can be built, tested, debugged and maintained reliably.

## Step 1: Understand the Product

Read the approved PRD and UI prototype.

Identify:

- Target users and primary user journeys.
- Required platforms and devices.
- Online versus offline requirements.
- Required native capabilities.
- Backend, database and external integrations.
- Security and privacy requirements.
- Expected scale and performance constraints.
- Deployment and distribution requirements.

Do not choose a stack before understanding these constraints.

## Step 2: Identify Hard Constraints

Determine which requirements are mandatory.

Examples:

- Must support iOS and Android.
- Must work offline.
- Must access a particular operating system API.
- Must support background tasks.
- Must run entirely on the local device.
- Must integrate with an existing Java backend.

Reject candidates that cannot satisfy a mandatory requirement.

## Step 3: Consider Developer Experience

Explicitly consider the user's known skills.

Prefer technologies that reuse existing knowledge when they
satisfy the product requirements.

Do not recommend a new language solely because it is popular
or because an AI model can generate its syntax.

Evaluate whether the user can debug generated code and maintain
the application after the initial implementation.

## Step 4: Compare a Small Number of Candidates

Normally compare two or three viable candidates.

For each candidate, explain:

- Why it fits the product.
- What the user must learn.
- What AI can reasonably implement.
- Which parts require platform expertise.
- Build, test, debug and distribution complexity.
- Dependency and long-term maintenance risks.
- Migration costs and limitations.

Use a weighted decision matrix where useful.

Do not let a high total score override a mandatory requirement.

## Step 5: Recommend One Primary Stack

Provide:

1. The recommended stack.
2. The reasons for choosing it.
3. The strongest alternative.
4. The trade-offs.
5. The conditions under which the alternative becomes preferable.

Avoid presenting a long list without a clear recommendation.

## Step 6: Validate Before Full Implementation

Create a small technical spike to verify the highest-risk assumptions.

Examples:

- Create and run a minimal application.
- Build the required platform target.
- Test a critical native API.
- Verify a backend connection.
- Verify offline persistence.
- Confirm packaging and signing requirements.

Do not assume that generated code compiles merely because it looks correct.

## Step 7: Record the Decision

Save the approved result in:

docs/architecture/technology-decisions.md

Include:

- Context and requirements.
- Candidates considered.
- Decision and rationale.
- Known limitations.
- Validation results.
- Conditions that would justify revisiting the decision.

Do not start full implementation until critical feasibility
risks have been addressed.

```

这份 Skill 的重点不是教 Agent 选择某个固定框架，而是约束它必须结合你的能力、产品需求和实际验证结果做决策。

另外，你可以在 `AGENTS.md` 里补充一条规则：

```
Before implementing a new application, invoke the
technology-selection skill after the product requirements
and platform constraints are sufficiently understood.

Do not choose a technology stack based only on familiarity,
popularity, benchmark performance or model preference.

Record the approved decision and verify the critical
technical assumptions before full implementation.
```

这样，技术选型就正式进入你的开发工作流，而不是每次临时想起来才问一次。

## 六、每次实际开发时，你应该怎么问大模型？

Skill 是长期规则，而下面这份是你在新项目中实际使用的提示词。

你只需要提供产品想法，模型就应该根据需求帮你选型，而不是把技术选择的工作重新推给你。

```

我准备开发一个新 App，请帮助我进行技术选型。

## 我的背景

- 我熟悉 Java 后端开发。
- 我对 JavaScript 有一定经验。
- 我不熟悉或不擅长部分客户端、原生开发及其他语言。
- 我会使用 AI 编程 Agent 辅助开发。
- 我希望最终交付一个真正可以运行、测试和发布的产品，
  而不只是生成一些代码。

## 产品想法

【在这里描述你的产品想法】

## 你的工作

请先理解产品需求，再推荐技术栈。

### 1. 分析产品约束

识别目标平台、核心功能、系统能力、离线要求、
数据存储、后端需求、发布方式和长期维护要求。

对于影响技术选择但尚未明确的信息，
先提出少量关键问题；可以合理假设的内容请标注假设。

### 2. 选择候选技术栈

根据需求选择 2～3 个真正可行的候选方案。

优先考虑：
- 是否满足产品需求。
- 能否复用我已有的 Java 和 JavaScript 经验。
- AI 是否容易辅助实现、测试和排查问题。
- 是否容易构建、启动、调试和发布。
- 长期维护成本及必要的新知识。
- 是否存在更简单的实现方案。

不要因为我熟悉 Java，就强行让客户端使用 Java。
也不要因为 AI 会写某种语言，就默认推荐它。

### 3. 做出明确推荐

请输出：
- 首选方案及理由。
- 备选方案及其适用条件。
- 各方案的主要优缺点。
- 我需要学习的新知识。
- AI 可以承担的工作和我需要重点审查的部分。
- 构建、测试、部署和发布的复杂度。
- 可能遇到的技术风险。

给出一个明确的首选方案，不要只罗列技术。

### 4. 验证技术可行性

在正式开发前，识别最可能导致项目失败的技术风险。

设计最小技术验证项目，验证关键平台能力、
依赖兼容性、构建流程和运行环境。

### 5. 形成技术决策文档

输出技术架构、技术栈清单、项目结构建议、
关键依赖、开发环境要求和技术验证计划。

将最终决策记录到：
docs/architecture/technology-decisions.md

## 约束

先完成技术选型，不要立即生成整个项目。

当关键技术风险尚未验证时，不要直接进入大规模编码。

```

## 七、最后，我建议你建立一个技术选型的“默认策略”

你不需要每个项目都从零开始评估几十种技术。可以先设定默认方案，再在需求确实不匹配时调整。

默认 1：业务型产品

Web 前端优先考虑 React + TypeScript，业务后端优先考虑 Spring Boot。适合管理后台、内容平台和大量表单、数据交互类产品。

默认 2：需要 iOS 和 Android 的 App

先比较 Flutter 与 React Native，重点考察实际平台需求、插件支持和你的前端经验，不要默认两套原生客户端。

默认 3：桌面工具

先比较 Tauri 与 Electron；若涉及深度系统集成，再评估 Swift、C# 等原生方案。

默认 4：复杂业务后端

优先利用你已有的 Java 经验。只有出现明确的性能、资源占用、运行环境或生态需求时，才考虑更换后端语言。

最后提醒你一点：技术选型并不要求你在开发前掌握所有技术，而是要求你知道哪些部分可以放心交给 AI，哪些部分必须通过实验和测试验证。

尤其是客户端开发，模型可以帮你生成页面和业务代码，但平台权限、后台运行、签名发布、数据迁移和系统兼容性，都需要实际验证。

因此，我最推荐你的完整流程是：

产品需求 → 技术选型 Skill → 原型 → 最小技术验证 → 分阶段开发 → 自动构建和运行验证。

这样既能发挥你已有的 Java 能力，也不会被自己不熟悉的客户端技术限制住。
