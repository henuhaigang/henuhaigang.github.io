进程挂掉排查方案2

31 Aug, 2026
| Edit page

从系统层面排查进程“挂掉”（崩溃退出或卡死无响应），核心思路是：先确认进程状态和退出原因，再查系统资源/日志/信号/核心转储，最后结合应用上下文定位根因。

以下按常见 Linux 环境给出实用步骤（Windows 类似思路可对应 Event Viewer、Process Explorer、WinDbg 等）。

1. 确认进程当前状态

# 查看进程是否还在、状态、占用资源
ps aux | grep <进程名或PID>
ps -eo pid,ppid,stat,wchan:30,cmd | grep <PID>   # 重点看 STAT 和 WCHAN

# 实时监控
top -p <PID>
htop

关键状态解读：

  • Z：僵尸进程（父进程没回收）
  • D：不可中断睡眠（通常等 I/O，可能卡死）
  • R/S：正常运行/可中断睡眠
  • 进程已消失：已退出或被杀

查看退出码（如果是自己启动的）：

echo $?          # 上次命令退出码
# 或从父进程/脚本日志看

2. 查系统日志和内核信息（最优先）

# 系统日志
journalctl -xe                    # systemd 系统
journalctl -u <服务名> -xe        # 针对某个服务
tail -f /var/log/syslog           # 或 messages、kern.log

# 内核消息（OOM、segfault、硬件错误等）
dmesg -T | tail -100
dmesg -T | grep -E 'oom|kill|segfault|Out of memory'

重点关注：

  • OOM Killer（内存不足被杀）
  • segfault / page fault
  • 硬件错误、磁盘 I/O 错误
  • cgroup 限制触发

3. 检查是否被信号杀掉

进程被杀通常会收到信号。常见信号：

  • SIGKILL (9)：强制杀，无法捕获（常由 OOM、手动 kill -9、cgroup）
  • SIGSEGV (11)：段错误
  • SIGABRT (6)：断言失败或 abort
  • SIGTERM (15)：正常终止请求

查看历史（如果开启了 audit 或进程有记录）：

# 审计日志（如果配置了）
ausearch -m USER_AVC,SYSCALL -ts recent | grep kill

# 或看应用自身日志是否有 “Received signal”

4. 核心转储（Core Dump）分析

如果进程崩溃生成了 core 文件，这是最直接的证据。

先确认系统是否允许生成 core：

ulimit -c                    # 应 >0，建议 unlimited
cat /proc/sys/kernel/core_pattern

生成后用 GDB 分析：

gdb <可执行文件路径> <core文件路径>
(gdb) bt                     # 看调用栈
(gdb) info registers
(gdb) thread apply all bt    # 多线程

也可配合 coredumpctl（systemd）：

coredumpctl list
coredumpctl info <PID>
coredumpctl gdb <PID>

5. 资源与限制检查

# 内存、CPU、文件描述符
free -h
cat /proc/<PID>/status       # VmRSS、VmSize、Threads 等
cat /proc/<PID>/limits       # 查看 ulimit
lsof -p <PID> | wc -l        # 打开的文件数
df -h                        # 磁盘是否满
iostat -x 1                  # I/O 是否打满

常见原因：

  • 内存泄漏导致 OOM
  • 文件描述符耗尽（ulimit -n）
  • 磁盘满、inode 耗尽
  • cgroup/memory 限制（容器环境尤其常见）

6. 进程卡死（Hang）专项排查

如果进程还在但不响应：

# 看它在等什么
cat /proc/<PID>/stack        # 内核栈
strace -p <PID> -f -tt       # 系统调用跟踪（看卡在哪个调用）
perf top -p <PID>            # 热点
gdb -p <PID>                 # 附加后 bt 看用户态栈

D 状态通常是等磁盘/网络 I/O，检查对应设备是否异常。

7. 其他系统层面工具

  • systemctl status <服务>：如果是 systemd 管理的服务
  • journalctl -b -1：看上一次启动日志
  • 容器环境：docker logs、kubectl describe pod、crictl，再进容器看
  • 检查依赖服务是否挂了（数据库、消息队列等）
  • sar、vmstat、pidstat 看历史资源趋势

排查优先级建议

  1. dmesg + journalctl → 是否被 OOM/信号杀掉
  2. 进程是否还在 + 状态（ps/top）
  3. 有无 core dump → GDB 分析
  4. 资源限制与系统负载
  5. strace/gdb 动态跟踪

如果你能提供更多信息（Linux 发行版？是否容器？进程是自己写的还是第三方？有无 core？日志里有什么关键字？），可以进一步缩小到具体命令和方向。
