深入理解 Java 双亲委派模型

一、什么是双亲委派模型

双亲委派模型是 Java 类加载器加载类时采用的一种层级委托机制。当一个类加载器收到类加载请求时，它首先不会自己去尝试加载这个类，而是把请求委派给父类加载器去完成。每一个层次的类加载器都是如此，因此所有的加载请求最终都会传送到最顶层的启动类加载器中，只有当父类加载器反馈自己无法完成这个加载请求（在它的搜索范围中没有找到所需的类）时，子加载器才会尝试自己去加载。

// ClassLoader.loadClass() 核心实现（简化版）
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1. 先检查是否已加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                if (parent != null) {
                    // 2. 委派给父加载器
                    c = parent.loadClass(name, false);
                } else {
                    // 3. 父加载器为 null，委派给启动类加载器
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 4. 父加载器无法加载，自己尝试加载
                c = findClass(name);
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}

类加载器层级结构

Bootstrap ClassLoader (启动类加载器)     ← C++ 实现，加载 %JAVA_HOME%/lib 下的核心类
    ↑
Extension ClassLoader (扩展类加载器)     ← 加载 %JAVA_HOME%/lib/ext 下的类
    ↑
Application ClassLoader (应用类加载器)   ← 加载 classpath 下的类
    ↑
Custom ClassLoader (自定义类加载器)      ← 用户自定义

二、双亲委派的好处

1. 避免类的重复加载

同一个类只会被加载一次，保证了 Java 核心库的类型安全。例如 java.lang.Object 无论被多少个类加载器请求加载，最终都由 Bootstrap ClassLoader 加载，全局唯一。

2. 保护核心类库不被篡改

防止恶意代码替换核心类。例如用户自定义 java.lang.String 无法生效，因为请求会委派到 Bootstrap ClassLoader，加载的是 JRE 自带的 String。

3. 类的隔离与命名空间管理

不同层级的类加载器形成独立的命名空间，同一个全限定名的类在不同类加载器中被视为不同类型。

4. 支持热部署与模块化

子类加载器可以卸载，实现类的动态替换（如 Tomcat、OSGi、Spring Boot DevTools）。

三、破坏双亲委派模型的场景与原理

虽然双亲委派是默认行为，但 Java 生态中存在多种“破坏”场景，主要分为三代：

1. 第一代：JDK 1.2 之前（用户重写 loadClass）

早期没有 findClass 方法，用户必须重写 loadClass 才能自定义加载逻辑，天然破坏了双亲委派。

2. 第二代：线程上下文类加载器 — SPI 机制

场景：JDK 核心库需要加载用户代码提供的实现类（如 JDBC、JNDI、JCE、XML 解析器）。

原理：

  • Bootstrap/Extension ClassLoader 无法访问应用类路径
  • JDK 提供 Thread.setContextClassLoader() 设置上下文类加载器（通常是 AppClassLoader）
  • 核心库通过 Thread.currentThread().getContextClassLoader() 反向加载用户实现
// SPI 典型加载方式（以 JDBC 为例）
public class DriverManager {
    static {
        loadInitialDrivers();
    }
    
    private static void loadInitialDrivers() {
        // 获取线程上下文类加载器（打破双亲委派的关键）
        ClassLoader cl = Thread.currentThread().getContextClassLoader();
        // 使用 ServiceLoader 加载 META-INF/services/java.sql.Driver 实现
        ServiceLoader<Driver> loadedDrivers = ServiceLoader.load(Driver.class, cl);
        // ...
    }
}

本质：父类加载器请求子类加载器完成加载，逆向委派。

3. 第三代：模块化热部署 — Tomcat、OSGi、Spring、JBoss Modules

Tomcat 类加载器架构

Bootstrap ClassLoader
    ↑
System ClassLoader (catalina.jar 等)
    ↑
Common ClassLoader (common/*.jar)          ← 共享库
    ↑
┌──────────────────┬──────────────────┐
WebappClassLoader  WebappClassLoader  ...  ← 每个 WebApp 隔离
(WEB-INF/classes)  (WEB-INF/classes)
(WEB-INF/lib)      (WEB-INF/lib)

破坏点：WebappClassLoader 优先自己加载，找不到再委派给父加载器（Common → System → Bootstrap）。

// WebappClassLoader 核心逻辑（简化）
@Override
protected Class<?> findClass(String name) throws ClassNotFoundException {
    // 1. 优先从 WebApp 目录加载（WEB-INF/classes, WEB-INF/lib）
    Class<?> clazz = findClassInternal(name);
    if (clazz != null) {
        return clazz;
    }
    // 2. 委派给父加载器（Common ClassLoader）
    return super.findClass(name);
}

// 但 loadClass 被重写以实现“先自己加载，再委派父加载器”
@Override
public Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    // 检查缓存
    Class<?> clazz = findLoadedClass0(name);
    if (clazz != null) return clazz;
    
    // 系统类（java., javax. 等）直接委派父加载器，保证核心库安全
    if (isSystemClass(name)) {
        return super.loadClass(name, resolve);
    }
    
    try {
        // 关键：先尝试自己加载（打破双亲委派）
        clazz = findClass(name);
        return clazz;
    } catch (ClassNotFoundException e) {
        // 自己加载失败，委派父加载器
        return super.loadClass(name, resolve);
    }
}

设计目的：

  • 隔离性：不同 WebApp 可使用不同版本同一库（如 Spring 4 vs Spring 5）
  • 优先加载 WebApp 类：避免 Common ClassLoader 污染
  • 保护核心类：java.*、javax.* 仍走双亲委派

OSGi / JBoss Modules / Spring Boot FatJar

  • OSGi：每个 Bundle 有独立 ClassLoader，形成网状依赖，按需导入导出包
  • Spring Boot FatJar：LaunchedURLClassLoader 优先加载 BOOT-INF/classes 和 BOOT-INF/lib

四、自己编写 ClassLoader 容易踩的坑

坑 1：不重写 findClass，而是重写 loadClass

// ❌ 错误：破坏双亲委派，且线程不安全
public class BadClassLoader extends ClassLoader {
    @Override
    public Class<?> loadClass(String name) throws ClassNotFoundException {
        // 直接自己加载，不委派父加载器
        byte[] data = loadClassData(name);
        return defineClass(name, data, 0, data.length);
    }
}

// ✅ 正确：重写 findClass，保留 loadClass 默认逻辑
public class GoodClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] data = loadClassData(name);
        if (data == null) throw new ClassNotFoundException(name);
        return defineClass(name, data, 0, data.length);
    }
}

坑 2：忽略 defineClass 的包封装限制

// ❌ 尝试定义 java.lang 包下的类会抛出 SecurityException
defineClass("java.lang.MyClass", data, 0, data.length);
// java.lang.SecurityException: Prohibited package name: java.lang

规则：defineClass 不允许定义 java.*、javax.*、sun.* 等保护包。

坑 3：类加载器死锁

// ❌ 多线程下并发加载同一类，可能导致死锁
public class DeadlockClassLoader extends ClassLoader {
    @Override
    protected synchronized Class<?> loadClass(String name, boolean resolve) 
            throws ClassNotFoundException {
        // synchronized 锁住整个加载过程，并发时极易死锁
    }
}

// ✅ 使用 JDK 内置的并发锁机制（ClassLoadingLock）
// JDK 7+ 已在 loadClass 内部使用 getClassLoadingLock(name) 细粒度锁

坑 4：资源加载不委派父加载器

// ❌ 只查自己的资源路径
@Override
public URL getResource(String name) {
    return findResource(name); // 忽略父加载器
}

// ✅ 遵循委派模型
@Override
public URL getResource(String name) {
    URL url = super.getResource(name); // 先委派父加载器
    if (url == null) {
        url = findResource(name); // 再查自己
    }
    return url;
}

坑 5：不考虑模块系统

Java 9+ 模块化环境下，ClassLoader.defineClass 需要指定 Module，否则类不属于任何模块，无法被模块化代码访问。

// Java 9+ 正确定义类到指定模块
Module module = ModuleLayer.boot().findModule("com.example").orElseThrow();
defineClass(module, name, byteBuffer);

坑 6：内存泄漏 — 类加载器持有引用

// ❌ 静态字段持有外部对象，导致类加载器无法卸载
public class LeakyClassLoader extends ClassLoader {
    private static final Map<String, Class<?>> CACHE = new HashMap<>(); // 强引用
}

// ✅ 使用弱引用或软引用
private static final Map<String, SoftReference<Class<?>>> CACHE = new ConcurrentHashMap<>();

五、编写自定义 ClassLoader 的最佳实践清单

事项建议
继承方式继承 ClassLoader，重写 findClass，不要重写 loadClass
双亲委派保留默认 loadClass 逻辑，除非明确需要破坏（如热部署）
包名限制避免定义 java.*、javax.*、sun.* 等保护包
并发安全依赖 JDK 7+ 的 ClassLoadingLock，不要加 synchronized
资源加载getResource / getResources 遵循委派模型
模块化Java 9+ 使用 defineClass(Module, String, ByteBuffer)
卸载支持避免静态强引用持有 Class 对象；使用 WeakReference 缓存
字节码来源实现 findClass 从文件、网络、数据库、加密流读取字节码
签名验证若需安全性，在 defineClass 前验证字节码签名/哈希
调试支持实现 getPackage 返回 Package 对象，便于工具分析

六、总结

维度双亲委派模型破坏双亲委派场景
核心原则向上委派，向下加载向下委派（SPI）、优先自加载（Tomcat）
解决问题类唯一性、核心库安全核心库调用用户代码、应用隔离、热部署
典型代表标准 Java SE 类加载JDBC/SPI、Tomcat、OSGi、Spring Boot
实现关键loadClass 默认逻辑重写 loadClass 或使用 ThreadContextClassLoader

一句话建议：

除非你在写框架/容器（Tomcat、OSGi、插件系统），否则永远不要破坏双亲委派模型；编写自定义 ClassLoader 时，只重写 findClass，其余交给父类。
