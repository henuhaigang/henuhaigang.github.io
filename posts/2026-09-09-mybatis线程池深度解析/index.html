MyBatis 线程池深度解析

核心认知：MyBatis 本身不创建线程池，但其 Executor 体系、BatchExecutor 批处理、ResultHandler 流式处理、异步调用 等机制与线程池深度交互。线上 90% 的 MyBatis 相关 OOM/死锁/超时，根因是 「业务线程池配置不当」+「MyBatis 批量/流式特性放大了资源压力」。

1.1 三种 Executor 对比

Executor创建方式PreparedStatement批处理适用场景线程安全
SimpleExecutor默认每次创建/关闭不支持通用增删改查✓ (无状态)
ReuseExecutorExecutorType.REUSE缓存复用 (Map<sql, PS>)不支持高频重复 SQL✗ (有状态，非线程安全)
BatchExecutorExecutorType.BATCH缓存复用 + addBatch支持批量插入/更新✗ (有状态，非线程安全)

关键警告：ReuseExecutor 和 BatchExecutor 非线程安全，严禁 在多线程共享 SqlSession！Spring 的 SqlSessionTemplate 默认使用 SimpleExecutor 并通过 ThreadLocal 隔离。

二、BatchExecutor：批量处理的「隐形内存杀手」

2.1 核心源码逻辑

// BatchExecutor.java
public class BatchExecutor extends BaseExecutor {

    // 缓存：sql -> BatchStatement (包含 PreparedStatement + 参数列表)
    private final Map<String, BatchStatement> statementMap = new HashMap<>();

    @Override
    public int doUpdate(MappedStatement ms, Object parameter) throws SQLException {
        Configuration configuration = ms.getConfiguration();
        StatementHandler handler = configuration.newStatementHandler(this, ms, parameter, RowBounds.DEFAULT, null, null);
        String sql = handler.getBoundSql().getSql();
        
        // 1. 获取或创建 BatchStatement
        BatchStatement batchStmt = statementMap.get(sql);
        if (batchStmt == null) {
            batchStmt = new BatchStatement(handler, ms.getParameterMap());
            statementMap.put(sql, batchStmt);
        }
        
        // 2. 绑定参数并 addBatch (核心：累积在内存中！)
        batchStmt.addBatch(parameter);
        
        // 3. 返回 0 (未真正执行)
        return 0;
    }

    // 统一执行所有批次
    @Override
    public List<BatchResult> flushStatements(boolean isRollback) throws SQLException {
        List<BatchResult> results = new ArrayList<>();
        for (BatchStatement stmt : statementMap.values()) {
            // 执行 executeBatch()
            int[] updateCounts = stmt.executeBatch();
            // 封装结果
            results.add(new BatchResult(...));
        }
        return results;
    }
    
    // BatchStatement 内部累积参数
    static class BatchStatement {
        private final List<Object> parameterList = new ArrayList<>();  // 无上限累积！
        private final PreparedStatement ps;
        
        void addBatch(Object parameter) {
            parameterList.add(parameter);  // 每次参数对象都保留引用
            // 绑定参数到 PS
            parameterHandler.setParameters(ps);
            ps.addBatch();
        }
    }
}

2.2 OOM 事故复盘：百万级批量插入

// ❌ 事故代码：一次性插入 200 万条
@Transactional
public void batchInsert(List<Order> orders) {  // orders.size() = 2,000,000
    SqlSession session = sqlSessionFactory.openSession(ExecutorType.BATCH);
    try {
        OrderMapper mapper = session.getMapper(OrderMapper.class);
        for (Order order : orders) {
            mapper.insert(order);  // 每次 addBatch，参数对象累积在 BatchStatement.parameterList
        }
        session.commit();  // flushStatements() 执行 executeBatch
    } finally {
        session.close();
    }
}

/*
内存分析：
- Order 对象：约 500 bytes (含字符串、BigDecimal 等)
- 200万 × 500B = 1GB+ 堆内存
- parameterList 持有所有参数引用 → GC 无法回收
- executeBatch() 时 JDBC 驱动再次复制参数 → 峰值 2GB+
- 结果：Young GC 频繁 → Full GC → OOM
*/

2.3 正确姿势：分批提交 + 清理

// ✅ 正确：分批提交，控制内存
public void batchInsertSafe(List<Order> orders) {
    final int BATCH_SIZE = 1000;  // 经验值：500-2000
    SqlSession session = sqlSessionFactory.openSession(ExecutorType.BATCH);
    try {
        OrderMapper mapper = session.getMapper(OrderMapper.class);
        int count = 0;
        for (Order order : orders) {
            mapper.insert(order);
            if (++count % BATCH_SIZE == 0) {
                session.commit();        // 执行 executeBatch，清空 parameterList
                session.clearCache();    // 清理一级缓存
            }
        }
        session.commit();  // 余数提交
    } finally {
        session.close();
    }
}

// ✅ 更优：MyBatis-Plus / 通用 Mapper 的批量方法 (底层同样分批)
@Service
public class OrderService {
    @Autowired OrderMapper mapper;
    
    public void batchInsert(List<Order> orders) {
        // MyBatis-Plus: insertBatchSomeColumn 默认分批
        mapper.insertBatchSomeColumn(orders);  
    }
}

三、ReuseExecutor：PreparedStatement 复用的双刃剑

3.1 复用机制源码

// ReuseExecutor.java
public class ReuseExecutor extends BaseExecutor {
    
    // 缓存：sql -> PreparedStatement
    // key: sql + parameterMap (配置级别)
    private final Map<String, PreparedStatement> statementMap = new HashMap<>();

    @Override
    public void close(boolean forceRollback) {
        // 关闭时释放所有 PS
        for (PreparedStatement ps : statementMap.values()) {
            try { ps.close(); } catch (SQLException e) { /* ignore */ }
        }
        statementMap.clear();
        super.close(forceRollback);
    }
}

// BaseExecutor.doQuery() 调用链
protected <E> List<E> queryFromDatabase(...) {
    StatementHandler handler = configuration.newStatementHandler(...);
    // ReuseExecutor 重写 prepareStatement()
    Statement stmt = handler.prepareStatement(handler.getBoundSql().getSql());
    // 实际执行 query
    return handler.query(stmt, resultHandler);
}

// ReuseExecutor.prepareStatement()
@Override
public PreparedStatement prepareStatement(String sql, ...) throws SQLException {
    PreparedStatement ps = statementMap.get(sql);
    if (ps == null) {
        ps = connection.prepareStatement(sql);
        statementMap.put(sql, ps);
    } else {
        // 重置参数 (关键！)
        ps.clearParameters();
    }
    return ps;
}

3.2 复用陷阱与风险

陷阱现象根因规避
连接泄漏连接池耗尽SqlSession 未关闭，PS 未释放，连接无法归还必须 session.close() / try-with-resources
参数污染错误数据clearParameters() 不彻底 / 并发共享严禁多线程共享 SqlSession
游标失效ResultSet closedPS 复用导致前序 ResultSet 关闭不要在同一 PS 上嵌套查询
DDL 失效表结构变更报错PS 缓存未失效，执行旧元数据DDL 后需刷新/重建连接

3.3 生产环境建议：默认不用 ReuseExecutor

// Spring Boot 默认配置
@Bean
public SqlSessionFactory sqlSessionFactory(DataSource dataSource) throws Exception {
    SqlSessionFactoryBean factory = new SqlSessionFactoryBean();
    factory.setDataSource(dataSource);
    
    // 显式设置 SIMPLE (默认就是 SIMPLE)
    factory.getObject().getConfiguration().setDefaultExecutorType(ExecutorType.SIMPLE);
    
    return factory.getObject();
}

// 如需 Reuse：仅在单线程批量任务中显式开启
@Transactional
public void singleThreadBatch() {
    SqlSession session = sqlSessionFactory.openSession(ExecutorType.REUSE);
    try {
        // 单线程串行执行，复用 PS 提升性能
    } finally {
        session.close();  // 必须关闭释放 PS
    }
}

4.2 线程池配置最佳实践

@Configuration
@EnableAsync
public class AsyncConfig {

    // 1. IO 密集型任务：数据库查询、HTTP 调用
    @Bean("ioTaskExecutor")
    public ThreadPoolTaskExecutor ioTaskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(50);           // 核心线程
        executor.setMaxPoolSize(200);           // 最大线程 (IO 密集可设大)
        executor.setQueueCapacity(1000);        // 有界队列防 OOM
        executor.setThreadNamePrefix("io-async-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.setKeepAliveSeconds(60);
        executor.initialize();
        return executor;
    }

    // 2. CPU 密集型：数据计算、报表生成
    @Bean("cpuTaskExecutor")
    public ThreadPoolTaskExecutor cpuTaskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        int cores = Runtime.getRuntime().availableProcessors();
        executor.setCorePoolSize(cores);
        executor.setMaxPoolSize(cores * 2);
        executor.setQueueCapacity(200);         // 小队列，快速拒绝
        executor.setThreadNamePrefix("cpu-async-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        executor.initialize();
        return executor;
    }

    // 3. 批量导出专用：长耗时、大内存
    @Bean("exportTaskExecutor")
    public ThreadPoolTaskExecutor exportTaskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);            // 少核心，防并发大事务
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(50);          // 极小队列，背压
        executor.setThreadNamePrefix("export-");
        executor.setRejectedExecutionHandler((r, e) -> {
            // 自定义拒绝：记录日志、降级、告警
            log.warn("Export task rejected, queue full");
            throw new RejectedExecutionException("Export queue full");
        });
        executor.initialize();
        return executor;
    }
}

4.3 异步服务实现：事务边界与 SqlSession 隔离

@Service
@RequiredArgsConstructor
public class ExportService {

    private final SqlSessionFactory sqlSessionFactory;
    private final ExportTaskExecutor exportExecutor;  // 注入专用线程池

    @Async("exportTaskExecutor")
    public CompletableFuture<ExportResult> exportAsync(ExportRequest request) {
        // 关键：每个异步任务创建独立 SqlSession (ThreadLocal 隔离)
        try (SqlSession session = sqlSessionFactory.openSession(ExecutorType.SIMPLE)) {
            OrderMapper mapper = session.getMapper(OrderMapper.class);
            
            // 游标流式查询，避免全量加载内存
            try (Cursor<Order> cursor = mapper.selectCursorByCondition(request.getCondition())) {
                ExportResult result = processCursor(cursor, request.getFormat());
                session.commit();  // 只读也建议 commit 释放锁
                return CompletableFuture.completedFuture(result);
            }
        } catch (Exception e) {
            log.error("Export failed", e);
            return CompletableFuture.failedFuture(e);
        }
    }

    private ExportResult processCursor(Cursor<Order> cursor, String format) {
        // 流式写入文件/压缩/上传，不累积内存
        try (OutputStream out = new GZIPOutputStream(new FileOutputStream(...))) {
            for (Order order : cursor) {  // Iterable 惰性加载
                writeOrder(out, order, format);
            }
        }
        return ExportResult.success();
    }
}

5.2 Cursor 游标模式 (MyBatis 3.4+)

// Mapper 接口
@Select("SELECT * FROM orders WHERE create_time > #{time} ORDER BY id")
Cursor<Order> selectCursorByCondition(@Param("time") LocalDateTime time);

// 使用
try (Cursor<Order> cursor = mapper.selectCursorByCondition(time)) {
    for (Order order : cursor) {  // 惰性迭代，每次 fetch 一批

六、线上事故案例复盘

案例 1：BatchExecutor + 并发导致连接池耗尽

// 事故场景：定时任务并发跑批
@Scheduled(cron = "0 0 2 * * ?")
public void batchJob() {
    // 10 个线程并发执行批量插入
    executorService.submit(() -> batchInsert(list1));  // BATCH Executor
    executorService.submit(() -> batchInsert(list2));
    // ...
}

/*
现象：
- HikariCP: "Connection is not available, request timed out after 30000ms"
- 数据库连接数飙升到 max_pool_size

根因：
- 每个 batchInsert() 创建独立 SqlSession (BATCH)
- 每个 SqlSession 独占一个数据库连接
- 10 并发 = 10 连接长期占用 (批量慢)
- 正常业务查询无可用连接

解决：
1. 串行执行批量任务
2. 或限制并发度：Semaphore(3)
3. 缩短事务：分批提交 + 及时 close()
*/

案例 2：ReuseExecutor 多线程共享导致数据错乱

// 事故代码：单例 Service 持有 Reuse SqlSession
@Service
public class OrderService {
    private SqlSession session;  // 单例！多线程共享！
    
    @PostConstruct
    public void init() {
        session = sqlSessionFactory.openSession(ExecutorType.REUSE);
    }
    
    public void createOrder(Order order) {
        OrderMapper mapper = session.getMapper(OrderMapper.class);
        mapper.insert(order);  // 并发执行时 PS 复用冲突
    }
}

/*
现象：
- 偶发 "Parameter index out of range"
- 数据错乱：订单 A 的数据插入到订单 B
- 查询返回错误结果

根因：
- ReuseExecutor 非线程安全
- 多线程共享同一 PreparedStatement
- 参数绑定互相覆盖

解决：
- 移除单例 SqlSession
- 每次操作 openSession/close
- 或使用 Spring SqlSessionTemplate (ThreadLocal 隔离)
*/

案例 3：大事务 + 长查询导致主从延迟

-- 事故：批量更新 50 万行，事务耗时 30 分钟
BEGIN;
UPDATE huge_table SET status=2 WHERE status=1;  -- 全表扫描 + 行锁
COMMIT;

-- 后果：
-- 1. 主库持有大量行锁，阻塞其他写入
-- 2. Binlog 积压，从库 SQL 线程单线程回放 → 延迟 2 小时
-- 3. 从库查询读到旧数据，业务报错

-- 解决：
-- 1. 分批更新 (每批 1000 行 + 间隔 100ms)
-- 2. 走索引：WHERE status=1 AND id > ? AND id <= ?
-- 3. 低峰期执行
-- 4. 考虑 pt-online-schema-change / gh-ost 无锁变更

7.3 Mapper 编码规范

// ✅ 好习惯
@Mapper
public interface OrderMapper {
    
    // 1. 显式列出列名，避免 SELECT *
    @Select("SELECT id, user_id, amount, status, create_time FROM orders WHERE user_id = #{userId}")
    List<Order> selectByUserId(@Param("userId") Long userId);
    
    // 2. 分页查询必须带 LIMIT
    @Select("SELECT id, user_id, amount FROM orders WHERE status = #{status} ORDER BY create_time DESC LIMIT #{offset}, #{pageSize}")
    List<Order> selectByStatusPaged(@Param("status") int status, @Param("offset") int offset, @Param("pageSize") int pageSize);
    
    // 3. 批量插入：rewriteBatchedStatements=true + 分批
    @Insert("INSERT INTO orders (user_id, amount, status) VALUES #{userId}, #{amount}, #{status}")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    void insertBatch(@Param("list") List<Order> orders);
    
    // 4. 大结果集：Cursor + fetchSize
    @Select("SELECT * FROM orders WHERE create_time > #{time}")
    @Options(fetchSize = 500)
    Cursor<Order> selectCursorByTime(@Param("time") LocalDateTime time);
    
    // 5. 更新必须有 WHERE 条件，防全表更新
    @Update("UPDATE orders SET status = #{status} WHERE id = #{id} AND status = #{oldStatus}")
    int updateStatusWithVersion(@Param("id") Long id, @Param("status") int status, @Param("oldStatus") int oldStatus);
}

九、12 年经验总结：MyBatis 并发避坑口诀

Executor 三类记心间：
Simple 无状态最安全，
Reuse 复用单线程，
Batch 批量分批提交。

线程池配置分 IO/CPU，
有界队列防 OOM，
拒绝策略要兜底。

事务边界要清晰，
@Async 别加 @Transactional，
编程式事务更可控。

大结果集用 Cursor/Handler，
fetchSize 要设置，
流式处理内存平。

连接池监控要全面，
活跃/等待/生命周期，
死锁超时快速失败。

批量任务串行跑，
分批提交清缓存，
索引走不走看 EXPLAIN。

   Interceptor 接点：Executor/StatementHandler/ParameterHandler/ResultSetHandler
